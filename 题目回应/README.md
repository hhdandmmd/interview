# 金融数据处理与特征工程：题目回应与设计说明

本项目将公开财报加工为可以查询、解释和复算的财务特征，服务于量化投研中的公司比较与因子研究。使用者在`config.py`中填写股票、数据来源和报告期，执行一次入口，程序自动完成采集、存储、清洗、特征计算和报告生成；回测按配置选择是否执行。

本文按[原题](../机试题目-金融数据处理与特征工程.md)说明**如何实现、为什么这样设计、结果在哪里以及能力边界**。只想先运行，请看[项目README](../README.md)；只想看产出，请在本地浏览器打开[示例结果入口](示例结果/index.html)。

## 一、整体方案与操作入口

### 1. 从业务问题出发

财报处理的难点不仅是取得数字，还包括三个问题：同一字段的单位与口径是否一致，跨期比较是否取到了正确季度，以及这些信息在什么时间才可以使用。因此，每个结果除数值外，还保留报告期、来源版本、可用时间、处理状态及依赖关系。

完整处理顺序如下：

```text
配置公司与报告期
  → 确定本次范围，补齐因子需要的历史季度
  → 低频采集三类财报，逐页保存原始响应
  → 校验结构与业务键，选择当前来源版本
  → 统一字段、单位和时间，清洗并记录问题
  → 计算财务特征，同时保存计算依赖与NULL原因
  → 检查覆盖率、缺失率、异常率和跨表一致性
  → 发布同一批次的数据库快照、CSV、Parquet、字典和HTML报告
  → 按需进行因子分组回测
```

这里的“快照”指一次固定的结果集合：财报、因子和解释均指向同一批次，后续来源更正不会悄悄改变已经交付的结果。

### 2. 面向使用者的配置

| 配置 | 含义与当前行为 |
| --- | --- |
| `stocks` | 自选一家或多家非金融A股公司，证券代码包含交易所，如`600519.SH` |
| `source` | 财报来源，默认`eastmoney`；当前真正接入的是东方财富 |
| `start_period / end_period` | 希望输出的财报季度；同比和环比所需的前期数据自动补齐 |
| `output_dir` | 数据库和结果工作区，默认`output/financial` |
| `backtest.enabled / factors` | 是否回测、分别回测哪些已生成因子；默认关闭 |
| 回测其他参数 | 交易日期范围、组数、持有交易日数、费用、时间口径和可选本地行情 |

完整Windows交付包解压后，双击最外层`run_demo.cmd`可离线复现固定样例；自选公司则编辑同层`config.py`后双击`run.cmd`。源码使用`python main.py`，依赖安装见项目README。日常操作无需直接管理数据库或学习维护命令。

目前覆盖人民币、自然年季度、合并口径的非金融A股财报。银行等金融企业的报表结构及指标含义不同，未套用普通工商企业公式；其他网站也需要实际开发接入后才可配置使用。

## 二、数据获取：来源、爬取和反爬策略

### 1. 数据源与三类财报

选择东方财富公开财报接口，原因是三类报表可以按证券代码与报告期取得结构化JSON，适合统一字段和重复采集。请求地址为`https://datacenter-web.eastmoney.com/api/data/v1/get`，请求参数指定报表、公司、期间和页码。

| 本地报表 | 来源报表标识 | 主要内容 |
| --- | --- | --- |
| `income`：利润表 | `RPT_F10_FINANCE_GINCOME` | 营业收入、营业成本、合并净利润、归母净利润 |
| `balance`：资产负债表 | `RPT_F10_FINANCE_GBALANCE` | 总资产、总负债、权益、流动资产、流动负债 |
| `indicator`：主要财务指标 | `RPT_F10_FINANCE_MAINFINADATA` | 加权ROE、披露毛利率、净利率、资产负债率和流动比率 |

采集按公司、报表与连续报告期组织请求，再读取全部分页。程序核对返回页数、条数、证券身份、报告期和必需字段，不能因为HTTP返回200就认定财报完整。若缺页或响应结构变化，该次采集记录失败及原文，不能把半份分页结果当成完整结果发布。

### 2. 基本反爬与故障处理

本项目采用低频串行采集，优先保证稳定性与可定位性。请求共用`requests.Session`，设置`User-Agent: Mozilla/5.0`和东方财富`Referer`，复用连接；默认相邻请求等待至少1秒、单次超时30秒、最多尝试3次。

| 情况 | 实际处理 | 设计理由 |
| --- | --- | --- |
| 正常请求 | 串行限频，连续期间合并查询，分页依次读取 | 控制访问频率，减少重复请求 |
| 超时、临时连接故障、408/429/500/502/503/504 | 有限次数重试并指数退避 | 短暂故障可以恢复，持续失败应明确退出 |
| 来源返回`Retry-After` | 兼容秒数和HTTP日期，同一来源共享冷却状态 | 换一家公司请求也不能绕过来源限流 |
| 需要等待超过本次等待预算 | 保留恢复时间与失败上下文，结束本次自动尝试 | 避免长期卡住，也不缩短来源要求的等待 |
| 403、证书错误、永久DNS错误 | 停止相应自动尝试；403阻止本次会话继续请求该来源 | 这类问题不适合连续重试 |
| 字段缺失、结构改变、分页不完整 | 保存原文和校验错误，阻止不完整输入进入正式发布 | 防止“请求成功、数据已经变错”的静默故障 |

这些措施覆盖原题要求的UA、限频及基本容错。当前没有实现验证码识别、代理池或登录态绕过；若来源增加此类要求，需要重新评估接入方式。

### 3. 原始数据持久化与恢复

每次HTTP响应先保存原始字节，再进行JSON解析；即使响应是错误页，也保留请求参数、状态、尝试次数和真实观察时间。逐页检查点用于确定中断发生在哪个公司、报表和页码。

原文文件与采集清单构成后续处理的依据，结构化结果存入工作区`catalog.sqlite`。这样既能联网采集，也能从同一份归档离线重放，排查清洗或公式问题时不必反复访问网站。采集会话未完成时，恢复会重新取得完整会话，不拼接两次抓取时间不同的分页。

原始字节摘要用于核对文件完整性，离线重放保留原观察时间；本次处理时间另记。文件校验并不证明网站给出的财务数字正确，金融正确性还需依靠后续规则及独立核对。

### 4. 采集规模与真实示例

随附小样例使用茅台、美的、格力三家公司，输入2024—2025年8个季度、3类财报，共72份报表。归档实际包含36个响应页，输出2025年4季度、每期15个特征，共180个特征位置，适合快速离线演示。

另完成沪深京50家非金融公司的实际采集验收：2022—2025年16个输入季度，预期2400个报表键，返回2353条，47条缺失。2023—2025年输出9000个特征位置，其中8482个有数值，518个保留NULL与原因。公司池是冻结样本，不宣称覆盖全部A股或完整历史股票池。

可直接查看[真实财务报告](示例结果/财务处理/report.html)、[小样例采集清单](../src/finpipe/resources/demo/manifest.json)和[50家公司实际统计](../data/evidence/full_market_capture_20261013/capture_analysis.json)。采集实现集中在[ingestion](../src/finpipe/ingestion)。

## 三、结构化存储与管理

### 1. 字段命名、类型与单位统一

来源字段集中映射为业务名称，每个字段同时声明来源名、单位、期间类型和转换系数。解析、清洗及导出字典共用这份规格，避免计算中使用一种单位、文档却写另一种单位。

| 来源字段 | 规范字段 | 存储口径 |
| --- | --- | --- |
| `OPERATE_INCOME` | `operating_revenue_ytd` | 人民币元，年初至本期累计营业收入 |
| `NETPROFIT` | `net_profit_ytd` | 人民币元，累计合并净利润 |
| `PARENT_NETPROFIT` | `parent_net_profit_ytd` | 人民币元，累计归母净利润 |
| `TOTAL_ASSETS` | `total_assets` | 人民币元，报告期末存量 |
| `ROEJQ` | `roe_weighted_ytd` | 百分数乘0.01转小数；例如12.3存为0.123 |
| `LD` | `source_current_ratio` | 来源披露的流动比率，单位为倍，不除以100 |

证券代码用字符串保留前导零和交易所；报告期使用准确季末日期；时间统一存为带时区的UTC时间。金额不猜测“万元”或“亿元”，遇到未声明币种或不支持的口径会记录问题。

字段规格位于[catalog.py](../src/finpipe/catalog.py)，实际导出字段见[本次数据字典](示例结果/财务处理/dictionary.md)。

### 2. 为什么采用原文文件、SQLite和CSV/Parquet

这三部分承担不同任务：

| 层次 | 保存内容 | 用途 |
| --- | --- | --- |
| 原始文件 | HTTP正文、请求与观察清单 | 保留来源依据、重放采集结果、定位上游变化 |
| SQLite | 来源版本、清洗结果、因子、依赖、运行与质量记录、发布快照 | 按公司和报告期查询，维护版本及一致性 |
| CSV / Parquet / HTML | 某次固定发布的表格、机器数据及可读报告 | 供Excel查看、Pandas/Arrow读取、面试演示 |

选择SQLite是因为本题规模不需要部署数据库服务，单个工作区即可移交；索引与约束支持公司、报告期和因子查询。原文保留在文件中，也避免将大段HTTP正文反复复制到每张业务表。

业务键由来源、证券代码、报告期、报表类型、合并范围组成。数据库逻辑上分为来源记录、清洗记录、特征及依赖、运行质量、发布快照几组；每组对应实际追溯或查询需求。旧版本保留，当前结果通过明确的版本选择和快照成员读取。

CSV采用便于Excel识别的UTF-8 BOM；Parquet明确字符串、日期、带时区时间戳和可空浮点类型，并在发布前回读校验。本题样本较小，每个数据集保存一份Parquet，避免按“公司×季度”切成大量小文件。未来数据量增长后再根据实际查询模式调整分区。

### 3. 公司与报告期查询

`query`按证券代码、报告期、因子查询当前可用快照；`explain`进一步返回公式依赖、来源版本、时间和NULL原因。所有查询固定同一发布集合，避免财务表已更新而因子表仍是上一批结果。

例如，[单公司单期查询](示例结果/财务处理/单公司查询.json)展示茅台一个季度的结果；[营收同比解释](示例结果/财务处理/因子解释.json)列出实际参与计算的报告期和字段。操作命令在[Windows说明](../docs/windows_usage.md)中给出。

### 4. 年报、半年报与季报如何组织

统一采用自然年季度：Q1为3月31日，Q2为6月30日，Q3为9月30日，Q4为12月31日。年报作为Q4保存，但不把全年累计收入误当成第四季度收入。

利润表是期间流量，保留年初至今累计值；资产负债表是期末存量，直接用于该期比率。单季利润表值由累计值拆分，具体算法在特征章节说明。披露的累计加权ROE也保留累计口径，不对ROE直接做季度差分。

## 四、数据清洗与标准化流程

### 1. 处理顺序与异常粒度

清洗依次校验证券及报告期、合并范围与币种、数值类型、财务阈值、时间证据和跨期可比性，输出规范值及对应状态。清洗函数只处理传入数据，不发网络请求或直接写库，便于对边界情况进行独立验证。

错误按影响范围处理：一个数值字段错误，只使该字段及依赖它的因子失效；公司身份、币种或合并范围不明确时，影响整条记录。原文始终保留，清洗不会覆盖来源内容。

### 2. 缺失值如何处理

`None`、空字符串、`--`、长破折号、`未披露`、`不适用`识别为来源缺失；不可解析文本、布尔值、NaN和无穷大识别为非法数值。整个必需字段从响应结构中消失，则属于来源契约变化，不能简单当成普通空值。

缺失不填0，也不在不同财报季度之间前填、后填或用平均数补齐。0可能表示真实经营结果，缺失表示没有证据，混用会直接改变利润率和增速。输出分别记录“缺报表”“来源空值”“非法值”“缺历史”“分母无效”等原因，使下游可以自行制定筛选策略。

### 3. 异常检测与处理规则

| 检查 | 规则 | 输出处理 |
| --- | --- | --- |
| 数值合法性 | 必须是可解析的有限数 | 非法字段置NULL，记录原因 |
| 资产与负债 | 总资产必须大于0；总负债、流动资产、流动负债不得为负 | 不合理字段置NULL，相关特征不可计算 |
| 极端ROE | 小数形式超出[-1, 1]，即±100% | 保留数值并标记warning，供审核 |
| 会计恒等式 | `abs(资产－负债－权益) > max(1元, abs(资产)×1e-6)` | 对有关字段记录勾稽警告 |
| 比率分母 | 金额分母默认须大于1元，比例基期须超过1e-8 | 过小或非正分母保留NULL，避免无意义放大 |
| 极端增长 | 增长类因子超出定义中的[-10, 10]范围 | 保留结果并记录极端增长警告 |
| 跨表指标 | 自算利润率、负债率和流动比率，与来源披露指标按口径核对 | 单列匹配、差异和不可比情况 |

负净利润可能是正常亏损，不因负数直接清除。极端值也可能真实存在，所以“明确非法”与“需要人工关注”分别处理，当前没有对财务值自动缩尾或截断。

[人工清洗反例](示例结果/清洗反例.json)展示未披露、坏数字、负资产、极端ROE和会计恒等式异常五种输入、预期及实际结果。这些是单独标注的人工案例，没有混入真实财务样例。

### 4. 去重、更正与最新版本

同一业务键可能重复抓取，也可能出现更正。项目把“内容版本”和“观察事件”分开：相同内容可以复用来源及清洗版本，每次实际抓取仍保留观察记录；完整新观察确认的唯一版本作为当前版本，旧版本可追溯。

若同一扫描对一个键出现不同内容，又缺少可靠排序证据，则记录冲突，不猜测谁更新。若最新版本有坏字段，下游显示新问题，而不是过滤坏值后退回旧好值。财报由A变成B、又恢复为A时，也保留这一观察过程。

公开接口不能证明完整的官方修订历史，因此本项目的“最新”依据完整采集观察，不仅凭`UPDATE_DATE`排序删除历史。跨期数据存在已知未解决重述或不可比风险时，相关增长及差分停止计算；一般尚未独立核验的可比性保留假设标识与警告。

### 5. 按实际发布日期对齐

每条财报区分以下时间：

| 时间 | 回答的问题 |
| --- | --- |
| 报告期末 | 这份财报描述哪个经营期间？ |
| 公告及已知更新边界 | 来源证据表明这一版本何时可公开获得？ |
| 真实观察时间 | 本系统什么时候实际取得该数据？ |
| 处理与发布时间 | 什么时候完成加工并提供给下游？ |

来源只有日期而没有准确时刻时，保守按上海时间次日零点放出；已有更新证据也纳入来源可用边界。特征可用时间由所有依赖共同决定，不能只看本期报表发布日期。公告证据缺失或不合法时记录原因，不用报告期或更新日期补造公告。

**教学例子：**假设2025年年报在2026年3月30日公告，不能在2025年12月31日就使用；只有日期证据时，来源边界为3月31日零点。若本系统10月才首次抓到，还不能说3月份已经观察到了这份数据。

因此默认`observed`按本系统真实已知及发布边界使用信号；历史研究可显式选择`publication_proxy`，按公告及已知更新边界近似放出。样例原始财报抓于2026年10月，当前值可能包含后续更正，**不能据此证明2023—2025年的严格历史PIT**。这一限制在数据与回测报告中保留。

### 6. 每条数据的清洗日志

清洗结果保存字段值、字段状态、原因、记录级状态、来源及清洗版本和处理时间；来源裁决另记选中、冲突或缺失。质量事件关联运行和阶段，便于从报告追到问题数据。

随附[清洗日志.csv](示例结果/财务处理/清洗日志.csv)从正式清洗版本导出，共72条。财报表中的`field_states`和`reason_codes`提供字段级解释。核心实现见[cleaning.py](../src/finpipe/transforms/cleaning.py)与[source_records.py](../src/finpipe/source_records.py)。

## 五、特征工程：公式、口径和扩展方法

### 1. 先拆单季，再做同比和环比

利润表累计值记为`YTD`，单季值记为`Q`：

```text
Q1 = 一季报累计值
Q2 = 半年报累计值 − 一季报累计值
Q3 = 三季报累计值 − 半年报累计值
Q4 = 年报累计值 − 三季报累计值
同比 = 本季值 / 上年同季值 − 1
环比 = 本季值 / 上一季度值 − 1
```

计算按准确报告期关联。缺少半年报时，不能把三季报减去一季报后当成第三季度；Q1的环比对应上一年Q4，需要正确取得上一年的年报及三季报。

**教学例子：**某公司一季报累计营收100、半年报累计230，则Q2营收为130；若上年Q2为100，同比为30%。程序存0.30，报告按30%显示。该例是公式说明，不是附带真实公司的财务数字。

### 2. 已实现的15个特征及金融含义

下面`R`为营业收入，`C`为营业成本，`N`为合并净利润，`P`为归母净利润；`q`表示单季，`ytd`表示累计，`lag1/lag4`表示准确前一季度/上年同季度。

| 特征标识 | 公式或取值 | 含义 |
| --- | --- | --- |
| `roe_weighted_ytd` | 来源披露的累计加权ROE | 股东资本盈利能力，按来源披露口径保留 |
| `roe_change_yoy` | `ROE_ytd / lag4(ROE_ytd) - 1` | ROE同比相对变化 |
| `roe_change_yoy_pp` | `ROE_ytd - lag4(ROE_ytd)` | ROE同比百分点变化 |
| `net_margin_q` | `N_q / R_q` | 本季度收入转化为合并净利润的比例 |
| `net_margin_ytd` | `N_ytd / R_ytd` | 年初至本期累计净利率 |
| `gross_margin_q` | `(R_q - C_q) / R_q` | 单季毛利率 |
| `gross_margin_ytd` | `(R_ytd - C_ytd) / R_ytd` | 累计毛利率 |
| `revenue_growth_yoy` | `R_q / lag4(R_q) - 1` | 单季营业收入同比增速 |
| `revenue_growth_qoq` | `R_q / lag1(R_q) - 1` | 单季营业收入环比增速 |
| `parent_profit_growth_yoy` | `P_q / lag4(P_q) - 1` | 单季归母净利润同比增速 |
| `parent_profit_growth_qoq` | `P_q / lag1(P_q) - 1` | 单季归母净利润环比增速 |
| `debt_asset_ratio` | `总负债 / 总资产` | 期末资产负债率 |
| `debt_asset_change_qoq_pp` | `资产负债率 - lag1(资产负债率)` | 杠杆水平的环比百分点变化 |
| `current_ratio` | `流动资产 / 流动负债` | 短期偿债覆盖能力，单位为倍 |
| `current_ratio_change_qoq` | `流动比率 - lag1(流动比率)` | 流动比率环比倍数差 |

原题的“净利润增速”在此明确为归母净利润增速；净利率使用合并净利润，两者不混算。加权ROE直接使用披露值，不用期末净资产近似重造一个同名指标。百分点变化存储0.02表示增加2个百分点；流动比率从1.2到1.5的变化为0.3倍。

### 3. 什么时候输出NULL

公式只有在准确依赖存在、字段有效、口径可比且分母满足条件时才返回数值。增长率要求正基期：若利润从-10变为5，直接计算会得到容易误解的“-150%”，所以本项目保留NULL，标记负基期及扭亏诊断；零基期也不强行生成增长率。

缺前期财报、最新版本冲突、已知重述未解决和非法分母分别返回状态及原因。普通可比性假设的警告可以伴随有效数值，读者可进一步筛选。NULL是有解释的业务结果，不等同于程序漏算。

### 4. 如何添加新因子

每个因子使用统一目录`features/factors/<因子名称>/`，其中`factor.py`同时维护名称、中文说明、公式、单位、准确期间依赖、异常范围和计算函数；`registry.py`显式登记。字典由同一份定义生成，减少公式改了而说明未改的风险。

新增因子的步骤是：

1. 写清金融口径、所需字段及期间；如缺字段，先补字段规格与来源校验。
2. 新建因子目录，实现`calculate(context)`，复用季度、比率和状态传递函数。
3. 注册因子，增加独立手算及边界案例，验证字典、依赖与输出。
4. 按口径变更维护公式版本及旧冻结运行的恢复兼容；源码改变后重新构建Windows程序。

计算函数不处理网络、SQL或文件。扩展一个因子无需复制采集和发布流程，也无需新增一套回测公式。可参考[营收同比因子](../src/finpipe/features/factors/revenue_growth_yoy/factor.py)及[完整维护说明](../docs/factors.md)。

## 六、附加项

### 1. 数据质量监控与核对

质量监控围绕“应有多少、实际得到多少、哪些值有问题、影响什么结果”设计，不能只统计已收到的数据。

| 环节 | 指标与检查 | 问题处理 |
| --- | --- | --- |
| 采集 | 预期报表键、返回数量、分页完整性、报表覆盖率 | 识别来源中断、缺页、范围不符和字段变更 |
| 清洗 | 按字段缺失率、非法率、异常状态、会计恒等式 | 定位具体公司、报告期和字段 |
| 特征 | 输出位置数、有值率、NULL原因、计算口径和依赖 | 区分数据问题、缺历史及数学无定义 |
| 跨批次 | 相同范围的行数变化、字段空值率变化 | 识别静默丢数，不把不同股票池直接相比 |
| 发布及运行 | 质量门禁、文件回读、任务心跳和发布状态 | 阻止问题批次冒充成功，保留诊断与恢复入口 |

覆盖率分母来自冻结的公司、期间、报表及适用范围，网站没有返回的数据仍在预期中。默认最低可用报表覆盖率为95%、最大字段非法率为1%；一般警告保留，超出门禁预算则阻止本次正式发布，具体指标及判断写入质量报告。

核对分为两类：一是同一来源内的资产负债恒等式、自算指标与披露指标核对；二是对独立原报告参考值的核对。后者随附[核对JSON](示例结果/原报告核对.json)：384个待核字段、34项参考，33项匹配、1项不可比，350项未覆盖。可比项为33/33匹配，不能据此声称所有字段都通过独立验证。

告警记录批次、阶段、表及数据范围、规则、来源证据、受影响下游和恢复建议。使用者可以从[质量报告](示例结果/财务处理/quality.json)定位问题，再通过`health`、`explain`及恢复命令处理。仅确认告警不代表已恢复，恢复需要后续扫描和规则重新验证。当前告警保存在本地，未接外部邮件或消息服务；本题的定期财报监控也不等同于盘中逐笔行情监控。

### 2. 增量处理与一致性

程序比较输入内容、来源裁决和处理口径，复用未变化的来源、清洗与特征版本。变化按公司在本次有限输出范围内重算，其他公司复用；即使数值相同，状态或依赖改变也不能误判成完全无变化。

日常入口仍会重新扫描配置的采集范围，以发现更正；“增量处理”不等于只追加新季度。高级`run --refresh recent`可以只刷新最近四个输入季度，但发布仍覆盖原输出范围。历史更正是否被发现，取决于实际扫描范围。

[样例运行验收](示例结果/运行验收.json)记录两次真实归档重放：首次计算180个位置；再次返回`NO_CHANGE`，新增来源、清洗及裁决版本均为0，计算0、复用180，保持同一快照。自动测试还比较同一最终输入的增量与全量结果，验证数值、状态及原因一致。

发布先固定数据库候选，导出并核验文件，再激活当前快照；中断后按保存的计划恢复。文件存在不代表发布成功，旧任务也不能覆盖较新结果。这保证“更正后重算”和“失败后重跑”仍维持同批次一致性。

### 3. 简单五组回测

回测用于观察因子排序是否对应不同收益表现。`backtest.factors`中的多个因子分别回测，共用行情，不将它们自动合成为多因子策略。

一次分组研究的流程为：

1. 在决策时点选择已满足时间条件的最新信号，按因子从小到大排序，等分五组；并列值按证券代码稳定排序。
2. G1为低值组，G5为高值组，组内等权。默认在下一交易日收盘进入，持有20个交易日，形成非重叠窗口。
3. 依据成员入场、退出价格计算收益，再计算组内平均收益；配置费用时扣除买卖两侧费用。
4. 按持有窗口累计净值，输出分组成员、各期收益、汇总指标及HTML/SVG图表。图有日期轴、净值轴、G1—G5图例和同截面等权参考。

缺入场或退出报价时保留成员，该组本期收益为NULL，后续累计净值停止，不删除坏股票或填0继续画线。回撤统计基于窗口端点，不能当作日频最大回撤；等权参考也是样本股票参考，不是沪深300等市场指数。

[公开样例回测](示例结果/分组回测/report.html)使用累计加权ROE，即`roe_weighted_ytd`，固定十家公司及腾讯后复权日线。请求区间为2023—2025年，因早期信号不足，实际形成20个窗口，持有范围2024-05-07至2025-12-24。可查[成员](示例结果/分组回测/memberships.csv)、[收益](示例结果/分组回测/period_returns.csv)及[净值图](示例结果/分组回测/nav.svg)。

该公开样例采用显式公告近似`publication_proxy`，历史财报版本未核验；默认`observed`仍使用真实已知时间。后复权报价的分红、股份变化尚未逐项核验，不额外加入分红现金流；未模拟撮合、停牌、涨跌停及成交限制。因此这是简单分组研究，不作为严格无偏、可成交或完整总回报的绩效证明。具体操作与口径见[回测说明](../docs/backtest.md)。

## 七、框架设计、可扩展性与工程取舍

模块按变更原因拆分，既方便维护，也使金融计算可以单独测试：

| 模块 | 负责什么 | 输入与输出 |
| --- | --- | --- |
| 配置与入口 | 校验公司、期间和参数，调用统一流程 | 使用配置 → 冻结运行范围 |
| `ingestion` | 网络请求、归档、分页和来源契约 | 来源请求 → 原文及观察清单 |
| `catalog / transforms` | 字段规格、规范化与清洗 | 来源行 → 规范值、状态和原因 |
| `features` | 准确季度、独立因子及依赖 | 清洗数据 → 特征与计算依据 |
| `storage / source_records` | 版本保存、最新裁决与查询 | 业务事实 → 可追溯记录 |
| `pipeline / publication` | 增量、门禁、发布与恢复 | 固定计划 → 一致的发布结果 |
| `quality / reconciliation` | 质量指标与核对 | 各阶段数据 → 质量报告 |
| `exports / backtest` | 导出报告与可选分组研究 | 固定快照 → 展示文件与研究结果 |

增加新数据源时，需要实现对应请求、分页与字段映射，明确币种、合并范围及时间证据，再通过同一清洗和计算链路验收。当前没有宣称“只改来源名称就能接任何网站”；保留清楚的接入边界比提前搭建通用插件平台更适合本题。

当前采用本地工作区、SQLite与单写入锁，网络请求放在数据库事务之外。没有引入分布式调度平台、消息队列或独立数据库服务；也没有为了潜在大规模场景提前增加Dask。保留的版本、质量和恢复结构分别服务于更正追溯、结果解释与失败恢复。

源码人工注释和docstring采用中文，重点解释口径、单位、NULL和设计原因。详细模块位置及维护入口见[架构说明](../docs/architecture.md)。
