# 代码与中文注释规范

用户明确要求：代码应可读、可维护、简洁高效，所有注释使用中文。此约定覆盖项目源码、测试、构建与调度脚本、SQL迁移、配置注释及文档中的代码示例。

## 1. 注释写什么

模块说明职责和外部资源边界；重要函数说明业务含义、单位、关键输入约束及失败/空值行为。金融计算必须能看出累计或单季、合并或归母、增长率或百分点差，避免读者从实现猜口径。

行内注释解释不能仅从代码看出的理由：为什么缺值不能填零、为什么季度缺口不能跨行关联、为什么源更新日期不能自动当作正式更正、为什么候选尚不能供消费者读取。只有必要时才列参数和返回值，不机械复制函数签名。

维护者需要知道的不变量应写在相应边界附近：原始证据不可变、最新坏状态必须失效、网络请求不在数据库写事务中、固定发布成员不可混读。说明实际存在的约束，不罗列未实现的未来能力。

## 2. 注释不承担什么

不要给赋值、循环、打印逐行配注释，不用空泛的“提高性能”“处理数据”替代具体理由。难以解释的长函数先拆清职责，再写注释。参数名、函数名和类型明确时，注释用于补充业务信息。

代码标识符采用一致的英文命名；HTTP/UTC、源字段名、库名及数学符号保留技术原名。第三方许可证与不可变源数据不是项目自写注释，保留原文。注释正文及 docstring 用中文，不强行翻译协议字段或更改数据内容。

## 3. 单一维护入口

| 变更 | 需要维护的入口 | 必须说明的内容 |
| --- | --- | --- |
| 新增/修改源字段 | 来源规格与规范映射 | 源字段、单位、可空性、适用性、证据与映射版本 |
| 新增清洗规则 | 规则函数与规则规格 | 触发条件、保留/置空/隔离、原因、影响字段及版本 |
| 新增因子 | 因子规格与计算函数 | 金融含义、精确期间依赖、单位、NULL原因及公式版本 |
| 修改时间规则 | 时间计算函数及 profile | 精度、时区、源事实、可用边界和旧快照冻结行为 |
| 修改发布/恢复 | 编排与存储边界 | 成功条件、中断状态、可见性、恢复输入和幂等依据 |

运行参数放配置，业务定义放规格和可阅读函数。字典由定义导出；README只说明怎么使用，不能再维护第二套公式、字段或默认阈值。

## 4. 评审与验证

代码评审检查三点：命名是否表达意图、注释是否解释真实业务约束、逻辑与说明是否一致。可用 Python tokenize/AST 枚举注释和 docstring 辅助检查，但含中文不自动代表说明充分；无需引入新的依赖或为了注释数量写测试。

纯注释修改做语法和必要回归即可，不新增镜像测试。金融或恢复逻辑改变时执行对应边界测试。保留人工手算与故障反例，测试预期不能由待测实现自行生成。
