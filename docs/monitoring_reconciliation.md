## 2. 数据核对：先证明可比，再比较数值

数据可信度需要同时证明键完整、语义一致、转换可复现和外部依据。核对复用quality事件/指标、输入血缘和证据文件，不新增一个独立对账服务。

| 核对层次 | 比较对象与目的 | 不可混淆的边界 |
| --- | --- | --- |
| 传输与归档 | 请求计划、页/键、原文摘要、解析行位置 | HTTP成功和总行数相同不证明键或值正确 |
| 规范转换 | 原字段×明示转换与clean值/状态 | 允许已声明转换，不允许任意改原值凑相等 |
| 财务勾稽 | A与L+E、流动资产/总资产等同口径关系 | 极端或勾稽偏差分级诊断，不机械删公司 |
| 同源交叉 | 自算累计比例与指标表 | 只证明同源内部一致，不能排除共用上游错误 |
| 独立原报告 | 规范科目与对应公开报告、页码/单位/修订版 | 版本及期间必须一致；公司原文缺失属于未核验 |
| 派生计算 | 特征与独立手算，增量与同事实全量 | 不调用待测公式生成预期 |
| 存储输出 | 同snapshot的SQL、CSV、Parquet、字典及manifest | 原文SHA只证明字节相同，不证明金额或口径正确 |

核对计划先冻结：左/右数据集及版本、源血缘、公司和报告期、科目、合并范围、币种、累计/季度/存量、修订依据、时间截止、单位转换、容差和参考证据。未知或不一致先标not_comparable，不把不同来源“净利润”直接连起来比较。

使用完整业务键外连接，先拒绝无效/空键和重复逻辑键；不能只inner join后宣称100%一致。pandas.merge支持validate检查关系及indicator区分两侧缺键，空键还可能彼此匹配；须在关联前显式隔离。[pandas官方merge说明](https://pandas.pydata.org/docs/reference/api/pandas.merge.html)

数值一致判断为：

~~~text
abs(left_value - right_value)
<= absolute_tolerance + relative_tolerance * max(abs(left_value), abs(right_value))
~~~

容差逐字段/规则声明单位并冻结。金额按原报告显示精度计入舍入界限，比率先统一为小数；不得对元、百分数、倍数统一给一个容差。相对误差分母为零时指标NULL，绝对差仍保留。两个缺失值表示both_missing，不能算数值匹配。

结果状态至少为matched、mismatched、missing_left、missing_right、both_missing、invalid_key、duplicate_key、not_comparable。记录左/右值、规范单位、差、容差、版本/页/字段定位、比较时间、原因、evidence_tier及影响因子。same_origin_check与independent_reference分别统计。

必须同时给计划对数、双边到齐数、语义可比数、已比较数、匹配/不匹配/缺键数及未比较原因。match_rate只在已比较有限数值对上计算；reference_coverage与comparison_coverage以冻结计划为分母，未知不排除。所有不可比都必须列示，不能用零比较或小交集制造“全部核验完成”。

金额不同先排查单位、版本/重述、合并范围、供应源和解析；修复映射开新profile重放，源更正保留真实证据，口径不明保留未核验。不能按谁更大、两源平均或谁抓得晚自动裁决。对应字段失效及门禁沿依赖传播；核对成功不是直接覆写结果表。

首版沿用既定真实门槛：两家公司独立合并年报核对，一家公司同年连续季度累计与单季核对。真实默认范围逐表勾稽、可比同源指标及固定产物核对进入正式流水线；缺独立原文的剩余公司明确未核验，不把抽样核验推广成全范围验证。

## 3. 财报任务的监控补强

财报作业在交易时间内运行也属于批处理。它的单位是run/batch；HTTP延迟与阶段耗时可以测，但NOTICE_DATE到接收的间隔是披露/抓取滞后，不是网络时延。固定2022—2025范围是历史样本，不能宣称它正在覆盖2026最新市场披露；改变范围建立新scope。

每个字段规格增加或明确update_policy：事件驱动、周期驱动、固定属性，以及应更新依据、检查频率、宽限和owner。扫描成功、源时间变化、金融值变化分别统计。财报原值持续不变不自动报警；若明确应取得的披露或已知更正长期未到，则依证据触发覆盖/新鲜度规则。

静态合法性和范围门禁始终执行。动态基线只从同scope、来源、字段和可比较profile的成功样本形成；受阻候选不更新基线。选用可读统计函数及规则参数，不增加异常检测平台。

动态指标可记录同季度/同报表的中位数、分位数和MAD、NULL率、跨期数量级变化；样本量、窗口、基线ID、统计规则和阈值须保留。不足min_samples标baseline_insufficient，只做硬规则和说明，不将缺基线写成通过。MAD=0不除零，改用已声明绝对差规则或标无有效尺度。亏损、极端比例和真实业务变动只警告，不能统计离群就覆盖财务值。

告警policy明确窗口、连续触发次数、去重键、冷却、影响范围、升级和连续恢复窗口。硬性源断裂、身份和血缘错误不因去抖延迟失效；低优先级波动可合并。确认、冷却、临时静默均不解除业务错误。持续故障按明确时长/影响升级，恢复需实际新结果及复查，不因单个正常采样立即resolved。

上述policy与rule/profile记录于现有规格和运行计划；本地告警仍是首版交付。外部通知接收方、授权和发送测试未配置，不能宣称已送达。

## 4. 盘中行情扩展：先定义真实源契约

这部分是面向岗位的扩展设计，未接入行情，未验证实时吞吐、未实现策略控制。财报的日频health和SQLite发布协议不能直接用作逐笔处理引擎。

接入前必须确定：交易所及品种、trade_date/session、行情类型（逐笔/快照/分钟）、订阅范围、时间精度/时区、序号作用域与重置、心跳语义、成交量/额单位及累计属性、重放/补包能力、快照覆盖边界、备用源和下游时延预算。数据源不提供某能力，就记录unsupported/unknown，而不模拟成真实支持。

沪深股票不同交易阶段应按交易所日历及证券实时状态确定，不能只写“工作日白天”。上交所公开时间区分集合竞价、连续竞价及休市，其他品种和场所须用对应规则。[上交所交易时间](https://english.sse.com.cn/start/trading/schedule/)

标准事件至少包括source/协议版本、channel、session/epoch、trade_date、security_code、message_type、原event_time及精度、received_at、processed_at、原序号（可空）、捕获定位、字段状态；本机排队/耗时另使用monotonic时钟，不与UTC混减。

| 检测 | 实施约束 |
| --- | --- |
| 源连接与心跳 | 通道是否存活；心跳持续不代表行情内容新鲜 |
| 内容新鲜度 | 通道、订阅集合和单证券分别判断；少成交/停牌不等于全源断流，快照与成交流期待频率不同 |
| 时延 | source→receive为跨钟表观差，须验证对时与误差；receive→process用本机单调时间；窗口给P50/P95/P99及样本数 |
| 完整性 | 只在实际协议定义的序号域检查；有界乱序等待后认定缺口，无连续序号不能声称逐笔零丢失 |
| 重复与乱序 | 同scope消息身份及摘要；相同序号不同内容不是普通重复，重连重置建立新epoch |
| 消息/字节/证券吞吐 | 按交易阶段、订阅及同时间段基线；首日无基线仍检查静态断流/积压 |
| 下游积压 | 有界队列长度、最老待处理年龄、消费吞吐及实际offset lag；无Kafka时不能虚构Kafka指标 |
| 数值/盘口 | OHLC、数量/金额、盘口层级及涨跌停等按品种和状态；占位值不当有效价，累计量按交易日/会话重置 |
| 分钟网格 | 先按日历、订阅和bar边界规则定义期望键，区分无成交、缺行情、尚未封口及迟到修订 |
| 监控本身 | 独立心跳、时钟、采样延迟和诊断完整性；不能监控进程卡死仍显示healthy |

不能直接按每股票last_seq+1检查所有源。所核验的深交所Binary Ver1.16示例规定，同频道逐笔委托/成交共用连续记录号；只订阅某证券或只看成交会出现合法跳号。该官方版本只用于说明协议作用域的重要性，接入时另冻结实际源版本。[深交所协议示例](https://www.szse.cn/www/marketServices/technicalservice/interface/P020240531617966177309.pdf)

事件时间窗口需要明确允许迟到范围、watermark证据和窗口修订政策；时间戳回退不一律视为源错误。分钟线写“左闭右开/右端标记”等精确规则，跨午休/隔夜不把缺时段填成正常数据。有界缓存满时必须报错/背压或按已声明策略降级，不能无声丢弃后继续声称完整。

所有阈值依据真实源频率、交易阶段、精度和下游SLA校准；分享对话的秒数/毫秒数只可作面试示例，不作为该项目生产默认值。

## 5. 盘中核对与恢复，区别当前可用和历史完整

未来盘中需增加三种核对：独立源同证券/同事件或允许时间偏差的对齐；同规则下逐笔聚合与封口分钟线；分钟与日线在成交范围、竞价/盘后、复权及单位一致时的聚合比较。快照成交量若为累计值，不能直接把每条快照相加。只有收盘价相同不足以证明全天数据完整。

跨源不按接收先后逐行相减，也不自动跨源补字段。备用源建立新source/epoch并校验语义、订阅与状态；不能比较两家的序号来“接续主源”。同一底层来源的两个客户端不构成独立校验源。

~~~mermaid
stateDiagram-v2
    HEALTHY --> DEGRADED: 新鲜度或延迟预算超限
    HEALTHY --> GAP_DETECTED: 确认连续性缺口
    DEGRADED --> RESYNCING: 有可用恢复证据
    GAP_DETECTED --> RESYNCING: 补包或快照接续
    RESYNCING --> HEALTHY: 当前状态验证及连续健康窗口通过
    RESYNCING --> UNRECOVERABLE: 缺重放或边界不可靠
    UNRECOVERABLE --> RESYNCING: 新证据或新会话
~~~

恢复固定缺口区间和受影响证券→下游标invalid/stale→按能力补包或用有明确序号覆盖的快照重建→丢弃快照已覆盖的重复增量→缓冲接续并核验连续/时延/盘口→新状态通知与下游复查。快照只恢复当前盘口时，current_state_quality可恢复，historical_completeness仍保持gap；不假装丢失成交已找回。不能将恢复标记回填覆盖故障期间。

下游质量标记包含scope/source/epoch、状态、原因、受影响字段、validated_at、valid_until、缺口和恢复证据。消费端按自身SLA验证过期，保留旧价只作last-known展示，不当正常当前信号。只有质量标记与新状态已可消费、恢复窗口通过才解除告警。交易开仓限制由实际策略/风控系统按其授权执行；本项目没有下单、平仓或自动切策略能力。

首个扩展纵向样例可用可核验的小段行情或清楚标识的人工事件，单独进程/目录保持有界状态并回放故障；与财报共享规格、事件和报告结构，不每tick写财报SQLite版本/快照，也不提前引入Kafka/Flink。全市场高吞吐能力须单独测量及存储设计，不能由财报样例推断。

## 6. 必须能发现的反例与完成状态

| 场景 | 必须表现 |
| --- | --- |
| 只inner join核对，右侧丢公司 | outer coverage发现missing_right，不能100%成功 |
| 两边NULL、万元与元、合并与母公司、不同重述版 | 分别both_missing/单位转换/不可比，不把它们数值相等即算核验 |
| 两客户端同源一起错 | same_origin_check不能升级独立证据 |
| 无交易/停牌/休市，但心跳持续 | 不按单股票无成交认定全源坏；按实际协议判断通道及内容 |
| 心跳持续但行情事件时间停住 | 内容stale，源连接正常不能解除 |
| 100、102、101在允许乱序范围内 | 缓冲核验，不能立刻把101永远判丢 |
| 按频道编号但仅消费单股票/单类型 | 合法跳号不冒充缺包；能力不足明确未知 |
| 重连序号归零、相同序号不同正文 | 分别新epoch与冲突，不被普通去重吞掉 |
| 事件时间比接收晚 | 时钟/精度诊断，不裁成0ms“正常延迟” |
| 输入正常、队列持续累积 | processing/oldest-age报警，源可用不等于下游及时 |
| 快照恢复当前盘口，原缺成交无法重放 | 当前可用可恢复，历史gap不可消失 |
| 切备用源或监控失联 | 新来源接续验证、valid_until过期，旧价不继续作正常输入 |

财务统一核对纳入正式主线验收A16，当前not_run。盘中扩展的真实接入、故障回放和性能验收按新scope另建检查；当前全部未执行，仅完成设计，不计入财报交付通过率。
