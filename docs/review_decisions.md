# 四方方案评审与裁决

本文保留首轮 v2 裁决历史。当前方案已通过[第二轮独立复审并修订为 v3](reviews/round2/decisions.md)，实施以现行主文档为准；下文的模式、命令和成员模型不能直接作为现行要求。

版本：2026-10-13，方案评审后 v2。评审对象是[评审前冻结文档](reviews/baseline/README.md)，不是已经完成的金融业务程序。用户要求完整、可维护、可扩展的面试项目；本轮据此取消以文件数和依赖数压缩工程职责的目标。

## 1. 评审组织与结论

四个 specialist agent 分别审查架构、数据口径、工程运行和测试交付，先形成独立意见，再根据主负责人裁决修订契约。共享问题合并解决，优先级按影响判断，不把四份报告的问题数相加当作风险数量。

| 评审 | 原始意见与侧重点 |
| --- | --- |
| 架构 | [架构评审](reviews/architecture_review.md)：责任边界、依赖、版本身份、发布完整性和范围 |
| 数据 | [数据评审](reviews/data_review.md)：财务公式、NULL/冲突传播、时点、字典、分母和输入依赖 |
| 工程 | [工程评审](reviews/engineering_review.md)：任务恢复、门禁、互斥、调度、存储、迁移与交付 |
| 测试 | [测试评审](reviews/testing_review.md)：可以推翻设计的反例、故障注入、验收及实际探测脚本检查 |

保留单机部署、Python、SQLite、三类财报和 15 个特征。完整项目增加真实维护所需的能力：明确数据字典、不可变处理版本、精确依赖、持久化批次、质量门禁、告警闭环、类型化 Parquet、调度健康检测、备份恢复和隔离 EXE。

方案不能靠评审证明“完美”。本轮解决的是设计歧义；可信度最终由实现和验收证据证明。

“已修订”只表示契约明确，不表示故障恢复、数据库或 EXE 已通过验证。原评审报告记录评审前状态，后来修订的处理结论以本表和 v2 文档为准。

最终交叉复核还补齐了三条约束：研究结果只生成独立研究产物，不激活生产发布/head；时间政策升级通过按 profile 的时间投影及快照冻结实现，不覆盖源事实或旧状态；实际 published_at 由激活事务及独立 receipt 提供，不在发布前封存的 manifest 中猜填。snapshot 成员既要对象引用唯一，也要满足业务键/特征键唯一；查询只连接所选快照的精确 clean 成员。

## 3. 完整与精简的边界

完整的是一条可维护的生产闭环，而不是占位功能的数量。第一版要求采集、清洗、入库、特征、时点、质量、发布、运行恢复和交付都落地；不将其中任意一项改成只有说明的演示。

暂不引入微服务、分布式 DAG、Kafka、Airflow、Dask、通用插件框架、配置化任意表达式、双主库或全资产数据平台。这些技术在当前 50 家财报量级不能补上正确性缺口，却会增加环境和排障成本。将来扩展通过职责边界和字典完成，不靠提前建设平台。

不要求每个函数都有类，也不要求每张表有一个 CRUD 文件。公共抽象应来源于已出现的重复维护问题；对少量不同报表用明确规格和适配函数比通用反射更易读。

## 5. 进入实现的顺序

先以实际 DDL、状态表及金融手算用例落实 P0，并同时打通最小 EXE 资源加载。接着构造跨季度离线完整流水线，验证源/处理版本、NULL失效、依赖与发布。再做真实多期采集、增量、故障恢复和告警闭环。最后提交字典/Parquet/SQL测量、隔离 EXE、在线核对和完整发布清单。

一周计划按这些验收里程碑推进，不能为赶时间删掉 P0 或宣布尚未执行的检查通过。若真实来源或交付环境受阻，记录实际阻断与已完成证据；选做回测排在主链路可信交付之后。
