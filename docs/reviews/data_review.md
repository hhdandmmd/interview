# 数据、财务口径与 PIT 独立评审

评审日期：2026-10-13。评审对象为原机试题、`architecture.md`、`data_contract.md`、`acceptance.md`、数据源验证脚本及保存的真实响应，并结合用户提供的岗位 JD。当前尚无业务流水线，下面的问题是需要冻结的设计契约，不能理解为已发现生产代码缺陷。

## 1. 评审结论

方案已经正确识别了财报处理中最容易出错的部分：营业收入与营业总收入不能互换，合并利润与归母利润要分开，金额累计转单季而资产存量与加权 ROE 不做差分，缺失季度不能靠行号位移补齐，亏损基期增长率不宜直接解释。保留源更新、公告和实际观察时间，并明确当前接口不能恢复完整历史 PIT，也是合理判断。

但目前还不能冻结实现。最主要的缺口是“版本选择以后数据变成不可用”的失效语义，以及覆盖率、字段新鲜度、字典与元数据的具体定义。这些是完整财务数据项目的必要能力，不能因样本只有几十家公司而省略；也不需要为了实现它们建设通用数据治理平台。

建议保留现有 15 个特征及三类报表，补齐下述 P0/P1 契约，再进入实现。无需增加期货、期权、多币种合并或通用因子 DSL。SQLite 历史版本管理仍适合当前量级，Parquet 可以作为有明确定义的分析交付格式，不承担版本裁决。

## 3. P0：实现前必须解决

### P0-01：冲突、无效更正必须使旧正常值失效

**位置：** 数据契约第 3、7、8 节；架构第 6、8 节。

文档规定保留历史版本、冲突隔离和 NULL 原因，但未明确“最新版本被隔离以后是否允许退回旧正常版本”。如果查询先过滤 `quarantined` 或 NULL，再选最新，昨天有效、今天发生冲突的记录仍会显示为正常数据。若增量只为成功计算的结果写特征，旧因子也会继续被下游消费。

**执行修订：**

1. 时点查询先过滤时间、裁决业务版本及冲突，再判断裁决结果的质量；禁止先删掉无效候选、再寻找较旧好值。
2. 区分“较旧数据晚到”“确证的新版本”“来源当前观测发生变化但无正式修订证据”“无法确定顺序的冲突”。`first_seen_at` 表示观察顺序，不自动构成公司更正证据；稳定 ID 只保证排序可重复，不能解决财务冲突。
3. 当前值变成 NULL、硬错误或冲突，也是有效的增量变化。为受影响特征写入新的 NULL 状态版本，记录该失效事件的可用时间；或显式保存旧版本有效区间的终点。不能只保存有数值的计算结果。
4. 没有可选输入版本的冲突要有业务键级别的时点状态。可用少量追加式选择记录保存“截至该时点选中哪个版本 / 为什么不可选”，不需要建设完整工作流平台。后续解决冲突时新增记录，不能回改当时的状态。
5. 最新报告本身无效时默认返回该报告的无效状态。确需使用旧报告的下游必须显式请求回退，并得到 `stale_fallback` 标记和报告期差距。

**验收例：** t1 的 Q2 营收为 240，t2 出现无法裁决的另一值。查询 t1 返回原值；查询 t2 返回冲突状态及 NULL，Q2/Q3 差分和相关成长因子同步失效。t3 解决冲突后恢复；t2 历史结果仍为冲突。无关偿债字段与无关公司不受影响。

### P0-02：时间模式、时间精度与计算版本必须纳入身份

**位置：** 数据契约第 1、7、8 节；架构的特征表及重建策略。

文档只明确公告精度字段，未明确更新日的精度处理；特征表唯一约束没有展开，也未说明规则、公式重建后如何避免混用结果。`observed` 和 `disclosure` 的同一报告因子可能数值相同但可用时间不同，不能共享一条未区分模式的结果。

**执行修订：**

- 公告和更新分别保存原值、精度、解释时区、规范时间及证据来源；日期精度统一转为上海时区下一日零点这个保守边界，再转 UTC。筛选使用 `available_at <= as_of`，日期型查询解释为该日结束；边界行为写入测试。
- `observed_available_at` 不早于真实快照首次观察时间和可信公告边界；`disclosure_available_at` 使用已声明的公告/更新边界规则，并持续标记历史修订未验证。
- 特征逻辑身份至少包含数据范围/来源、证券、报告期、特征、时间模式、公式版本及清洗规则版本；物化版本另包含确定性输入版本摘要。两种模式不能互相覆盖。
- 区分 `available_at`（所用数据何时可知）和 `computed_at`（何时计算）。用新公式计算过去保存的输入时，可以得到回溯研究结果，但必须显示新公式版本；若承诺还原“系统当时实际产出的结果”，还须限定当时的计算/发布版本。
- 源日期缺失、时间冲突的处理要明确：可保留财务记录供查询核验，但不能通过填报告末日让它进入宣称按公告对齐的结果。查询不得默默切换模式。

**验收例：** 同一证券及报告期分别生成两种模式，结果均保留；更新字段只有日期时，该日盘中查询不得提前使用更新版本；升级公式不能改变旧公式的历史结果。

## 4. P1：完整交付必需补齐

### P1-01：从字段映射表补齐可维护的数据字典

现有文档很好地解释了金融字段，但缺少运行表、版本字段、状态字段和质量指标的完整字典；币种、合并口径、行业标签的证据与未知状态也未定义。

建议在 `contracts/` 或一个职责明确的契约模块中，维护三类静态规格：报表字段、特征、质量规则。使用普通类型化结构即可，无需外部元数据服务。映射、字段校验和字典导出读取同一份规格；复杂财务公式仍写成普通函数，不能塞进字符串表达式求值器。

每个字段至少声明：表名、规范名、业务说明、类型、NULL 语义、存储单位、展示单位与倍数、来源报表/字段、转换方法、必需键或可空、适用范围、质量规则、依赖下游、字典版本。每张运行表补充主键、唯一约束、外键、时间语义、保留策略及主要查询方式。

特别补充以下定义：

| 字段/概念 | 需要冻结的口径 |
| --- | --- |
| `consolidation_scope` | 保存 `scope_evidence`；报表名作为供应商口径证据、正式报告作为独立核验证据。未知不能直接改成 consolidated |
| `organization_type` / 行业 | 分开保留组织类型与行业，行业注明提供方、分类体系、分类版本和观察时间；`unknown` 不默认为非金融 |
| `currency` | 不从金额数值猜币种；源币种缺失要有独立声明证据或不可计算状态 |
| `feature_unit` | 分别定义存储单位与展示单位。`_change_pp` 存 0.02 时，存储是比率差，展示为 2 个百分点，不能让下游把 0.02 当 0.02 个百分点 |
| `revision_history_verified` | 表示什么证据完成了何种历史验证；观察到两个版本不等于该报告所有历史版本齐全 |
| `restatement_basis_unverified` | 进入可导出的证据标记；不能只有文档提到而结果丢失 |
| NULL 及状态 | 适用性先判定；其余错误按确定优先级产生主状态，并保留完整原因列表。缺历史、字段缺失、分母无效不能混成一类 |

金融适用性判定未知时，记录名单排除或等待核验的原因。银行不适用样例应带真实分类证据，不能只因字段恰好为 NULL 就认定不适用。

### P1-02：覆盖率需要独立于字段缺失率的期望集合

现有“期望/实际数量”不足以落地。50 × 16 × 3 只能叫配置理论网格；新上市公司、源覆盖不足、未披露和请求失败的含义不同。

每次运行持久化 `universe` 与 `expected_keys` 清单，业务键为公司、季度、报表类型、口径。记录样本选择依据、观察时间、行业/交易所标签、应请求范围及不能确认历史资格的原因。无法证明某季度应有报告时标记资格未知，不能直接宣称企业漏披露；但本次计划请求的键仍须统计请求完成率。

建议固定以下指标，并同时输出分子、分母：

| 指标 | 定义 |
| --- | --- |
| 采集完成率 | 成功完成请求的计划分片 / 计划分片；合法空响应也必须单独计数 |
| 报表覆盖率 | 返回可识别业务记录的不同键 / 本次应取得的业务键；资格未知单列 |
| 可用报表率 | 可供相关计算的不同键 / 本次应取得的业务键；隔离不能算成功 |
| 字段缺失率 | 收到记录中适用字段缺失数 / 收到记录中该字段适用数 |
| 因子数值覆盖率 | `ok` 或可消费 warning 的非空因子键 / 输出范围内适用因子键 |
| 因子原因分布 | 缺报表、缺比较期、分母、冲突、错误、不适用分别计数 |

没有收到整张报表不会进入“收到记录的字段缺失率”，因此必须同时展示报表覆盖率。分母为零时输出 NULL 和 `not_applicable`/`no_eligible_records`，不能显示 0% 缺失或 100% 覆盖。比较运行必须匹配范围、字典/规则和统计粒度。

**验收例：** 计划 10 个报告键，返回 9 条且字段均完整，报表覆盖率 90%，字段缺失率 0%；只有前者揭示整条缺失。

### P1-03：字段更新频率必须符合财务数据的事件特征

JD 明确要求更新频率，但当前方案仅有数量、缺失与异常率。财报是低频事件数据：一个旧报告一年没有改值可能完全正常，把“距离上次金额变化”作为故障指标会持续误报。

至少区分以下时间并纳入运行摘要：`last_checked_at`、`last_successful_fetch_at`、`last_observed_change_at`、`latest_report_end`、`latest_disclosed_at`、本次增量新增/更正数。字段值变化率按同一范围的有效字段配对计算；NULL→有值、有值→NULL 单独统计。

新鲜度告警分别针对计划任务迟到、采集连续失败、应到的新报告缺失、契约变化及异常字段集体停更。历史固定范围采集不要求每次出现新财报；“应到”应依显式监控范围、源端可观察披露事件或可解释的配置规则，不从固定年报截止日臆造公告事实。

首版通过退出码、结构化告警文件与 HTML 实现本地闭环就足够。每条告警包含 run、分片、表、公司/报告期、规则、实际/阈值、影响特征及恢复命令；默认不接外部通知平台。

### P1-04：原始、业务、清洗与计算版本摘要要分开

架构把公告/更新元数据纳入业务摘要是可行的，但缺少数字规范化与清洗版本身份。`1` 和 `1.0`、字段顺序、负零、原始日期字符串格式不应制造假财务修订；映射或清洗规则变化也不应写成“上游数据更正”。

冻结以下少量身份即可：

- `raw_hash`：真实响应字节摘要，用于归档校验。
- `source_record_hash`：业务键、规范数字/日期、单位及声明的修订元数据的稳定摘要；明确字段白名单、排序、缺失标记与数值序列化。不是把全部源 JSON 字段排序后直接当业务版本。
- 清洗结果身份：`source_version_id + mapping_version + cleaning_rule_version`。新规则重建不覆盖旧清洗结果，也不修改原始 `first_seen_at`。
- 特征身份：特征/规则/模式版本及有序依赖摘要。输入原值不变但适用性、时间边界或规则改变时，仍可产生正确的新派生结果。

公告/更新发生变化而金额不变时，记录 `metadata_changed`，与财务字段 `value_changed` 分开统计。实际保存原始字节时，要保留抓取的响应正文；探测脚本当前保存的是解析再序列化的 JSON，它适合作为字段证据，不能标成原始 HTTP 字节证据。

### P1-05：依赖窗口和增量传播需要冻结到原始累计字段

默认 2022 年上下文足以支持从 2023Q1 输出的现有特征，但用户改变范围时，“输出是采集范围的子集”仍不保证因子可计算。单季同比不仅需要前一年同季度，有些季度还需要两个期间各自的上一累计期。

为 15 个特征给出到原始字段/精确报告期的依赖清单，可由少量累计转单季与期间偏移函数展开，不需要通用 DAG 引擎。配置预检展示所需上下文，允许用户选择补采或明确接受 `missing_history`；不能按现存行数估计历史长度。

以 Q2 累计营收修改为例，可能受影响的单季营收为 Q2 和 Q3；单季环比目标涉及 Q2、Q3、Q4；下一年 Q2、Q3 的单季同比亦受影响；Q2 的累计毛利率/净利率和依赖 Q2/Q3 单季营收的利润率也须处理。还要包含从缺失变成有值、从有效变成不可用的变化。具体集合按已注册特征的字段依赖决定，不能只有这段示例清单。

缺失历史的因子也登记其“期望依赖键”，或能够从特征规格推导。否则以后补到缺失报告，既有成功输入关系里找不到该报告，会漏算之前为空的结果。

### P1-06：独立核验与结果可解释性要超出单年报同源校验

当前三家年度指标同源吻合是有效证据，但季度累计性质、合并口径、重述基础、行业适用性尚未完成独立验证。建议保留验收中的两家原报告核验，再至少加入一组同年度 Q1/Q2/Q3/年报的人工核对记录，确认源金额累计口径和季度差分；保存核验来源、页码、币种、口径、数值、差异及结论。

如果当前源数值与旧年原报告不一致，先判断重述或修订证据，不能为“对齐”直接覆盖来源值。没有证据时输出待核验差异及影响范围。

结果提供 `explain` 或等价查询：给定公司、报告期、特征和时点，展示原始输入字段、输入报告期/版本、可用时间、公式与空值原因。这个能力可由既有 `feature_inputs` 和字典实现，通常比再添加一批因子更能说明可维护性。

目前采集历史财报的实际观察时间集中在 2026 年，不能据此生成 2023—2025 年真实 observed 回测。应完成因子表和严格时点查询，并使历史快照不足的回测明确拒绝执行。演示历史更正使用注明身份的测试夹具，不伪装成真实历史快照。

## 5. P2：增强项及边界

| 项目 | 建议 |
| --- | --- |
| Parquet 分析交付 | 输出与 CSV 同口径的类型化财务和特征表，带 manifest、字典/公式版本、行数与文件摘要；当前量级每张表每次发布一个文件即可，不按证券和季度制造大量小文件。增长后再以报告年等较粗粒度分区，并记录实际读取性能 |
| 金融统计质量 | 在硬规则之外加入同业/同报告期稳健统计和源端指标差异检查；小样本只输出诊断，不能把行业离群自动当错误或覆盖原值 |
| 更多财务因子 | TTM、自主 ROE、经营现金流等后续扩展需新增口径和依赖测试，不为凑数量临时加入。优先交付 15 个现有特征、失效传播和可解释查询 |
| 完整历史 PIT | 将“从开始真实采集以后可审计”与“供应商历史修订全覆盖”分别命名。后者需要正式历史版本证据，不能靠设计了版本表就宣称实现 |

## 6. 可直接冻结的交付清单

在业务代码开始前补齐：字段/表/特征/规则字典、公司池与期望键定义、时间精度与版本裁决规则、NULL/冲突失效规则、原始依赖展开清单。实现交付应同时产出运行 manifest、质量指标和告警、因子输入追溯、真实财报核验记录。

数据方面的验收重点为：两种模式互不覆盖；更正/冲突/失效/补缺均传播；旧正常值不会静默复活；整批缺报表可被覆盖率发现；固定历史报告不因未变化而误报；同一源版本在新规则下的派生历史仍可区分。满足这些条件后，现有规模即可形成可信、完整且便于维护的项目，无需扩大数据量来证明工程能力。
