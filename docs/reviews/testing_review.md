# 独立测试与交付验收评审

评审日期：2026-10-13，Asia/Shanghai。角色：测试与交付验收。评审对象为 `docs/reviews/baseline/` 中冻结的架构、数据契约、验收与源验证文档，以及机试题、岗位 JD、现有 `scripts/probe_source.py` 和三个真实证据 JSON。评审前未阅读其他 agent 的报告。本轮没有实现业务流水线，没有调用真实外部告警，没有联网重采或覆盖真实证据。

## 1. 结论与已具备的基础

方案具备合理的工程基础：金融累计口径、精确季度关联、披露与观察时间分离、保留来源版本、增量依赖传播、原始页先归档、输出先暂存再发布，都是应保留的设计。现有验收文档也诚实区分了“计划验收”与“已经通过”。无需通过引入任务平台、分布式计算或全资产类型来改善这份面试项目。

目前尚不能认定方案已经完整闭合。最重要的修订是明确处理版本的身份、无效/冲突更正的失效语义、固定快照下增量与全量一致性的判定，以及提交后导出失败的恢复状态。岗位 JD 中占比较高的质量告警与定时任务未执行风险，也需要可运行、可演示的闭环验收，而不止最终 HTML 报告。

优先级含义：P0 为实现前必须确定、否则可能输出错误金融结果的设计问题；P1 为最终交付前必须验证的可信度与恢复问题；P2 为增强证据、维护效率或实现安排的改进。这里的 P0 是设计阻断项，不表示尚未实现的代码已经发生故障。

## 2. 主要问题与可执行验收

### T01 · P0 · 来源版本与处理版本尚未形成可保存的身份

位置：`baseline/architecture.md:149–153`、`:158`、`:193`；`baseline/acceptance.md:53`。

三张 `clean_*` 表只有 `version_id` 主键，而同一源版本在清洗阈值、映射或规则变化后可能有不同结果。业务摘要又包括“映射后的业务值”，映射修正可能被误记为新的源更正，与“计算版本变化不是源数据变化”目标冲突。`runs` 中保存版本号不足以保证旧清洗结果和其因子依赖仍可查询。

反例：源金额不变，第一次错误按万元解释，后来映射修为元；或源资产恒等式误差第一次接受，阈值收紧后隔离。若更新原清洗行，原运行不可复现；若生成新 `report_versions`，来源变更计数被污染；若不更新，规则改变无法生效。

建议明确两种身份：不可变来源记录/内容版本，以及以来源版本、映射版本、规则版本等组成的处理版本。因子依赖指向实际使用的处理结果，导出记录明确的规则/公式组合。是否按当前规则重建历史数据与是否复现历史服务结果，是两种查询诉求，必须由规则选择或运行快照区别，不能仅按 `available_at` 混在一起。

验收：固定一份真实原始页，按规则 A、B 运行；来源版本数、新增/变更计数保持不变，处理结果可不同，A/B 的结果均可回查。再分别以 A、B 从零重建，对应增量结果完全一致。旧 `run_id` 的结果仍与原发布清单相符。

### T02 · P0 · 最新更正无效或冲突时，旧有效值是否失效未定义

位置：`baseline/architecture.md:160`、`:184–189`；`baseline/data_contract.md:76`、`:90`、`:170`。

文档定义了隔离与 `version_conflict`，尚未定义业务键/字段的现行状态和有效区间。查询若先筛选“accepted 且非空”再取最新，会退回旧值；增量若只插入成功计算的因子，会把旧的正常因子继续留在最新输出中。

反例：Q2 营收先为 240，更正为 null，或更正为无法解析的金额。Q2/Q3 的季度差分及其环比、次年同比应在更正可见后变为空并带原因；此前的历史查询仍保留旧值。同一天出现 240/260 且无法判定顺序时，也不能悄悄继续发布“240、ok”。

建议：先确定截至时点的业务版本/冲突状态，再按其清洗有效性计算。证明是更正的新无效值应产生失效或 NULL 特征版本；无法证明先后的冲突需要明确的冲突状态和下游传播策略。可以保留历史或供诊断查看的旧值，但不能把其作为当前无争议的有效结果。仅有源页获取失败则属于来源暂不可用，不能凭此判定已知有效事实被撤回；必须区分获取失败、明确无效更正、冲突和真实撤回。

验收：同一夹具依次注入 `240 → null → 260`、`240 → 非数值 → 260` 和相同时间证据的 240/260 冲突；每个观察边界前后查询来源、清洗和因子。新时点的受影响 NULL/冲突结果必须实际替代旧有效行，无关字段和公司不变；修复后解除冲突/错误；历史时点的旧结果不变。

### T03 · P1 · 增量验收缺少固定快照下全量对照的判定依据

位置：`baseline/architecture.md:184–193`；`baseline/acceptance.md:51–53`、`:62`。

目前用一个“更正 Q2 累计营收”的案例说明传播正确，无法覆盖不存在的依赖节点、缺值变有效、有效变错误、跨年 Q1、旧版本晚到、公式版本变化和多次更正。重跑后“值不变”也不等于依赖、状态、可用时间都正确。

反例：某公司最初缺 Q1，因此未产生 Q2 单季与 Q3 环比；后来补入 Q1。仅查历史 `feature_inputs` 会漏掉最初未生成的节点。另一个反例是将 Q2 从有效值更正为缺失后，旧 Q3 环比未被删除或置空。

验收方法：构建 2 家公司、至少 6 连续季度、3 类报表的固定人工事件序列，包含重复、乱序、迟到、更正、缺失恢复、冲突、无效更正及规则改变。路径 A 顺序增量；路径 B 在新数据库重放相同原始事实与观察清单，全量重建。固定相同 `as_of`、范围、时间模式、处理和公式版本，比较排序后的业务键、值、状态、单位、`available_at`、输入版本集合；只排除 `run_id`、耗时、发布路径等运行元数据。浮点有限值按明确容差比较，NULL/状态/时间/依赖集合要求精确一致。对每次事件后的检查点都比较，不能只比较末次结果。

另测输出窗口之外的历史更正：重叠扫描未发现时报告扫描限制；显式深度刷新后传播正确。全量对照使用同一已归档快照，不能重新联网获取变动中的数据作为判定依据。

### T04 · P1 · 数据库提交与文件发布之间需要可恢复状态及崩溃检查点

位置：`baseline/architecture.md:189`、`:195`、`:222`；`baseline/acceptance.md:56`。

“事务中断无半批数据、导出中断不更新成功指针”方向正确，尚未规定事务已经提交、导出失败后的运行状态，以及进程在更新 `latest.json` 前后退出时如何判定结果。若失败事件只与业务数据同一事务提交，回滚还可能丢失失败定位信息。

建议定义最少必要的状态与恢复动作，例如采集中、已提交待发布、已发布、失败/部分失败；记录发布清单和阶段检查点。无需通用工作流引擎，但恢复必须能够辨认“重采/重算”和“仅重新导出”。失败上下文应在业务事务失败后仍可保存。暂存目录与最终目录放同一输出根路径，发布单一不可变运行目录，最后更新成功指针。

验收：在临时目录分别注入原始页落盘后、数据库提交前、提交后、CSV 完成但 HTML 未完成、运行目录改名后、成功指针更新前/后等中断。使用子进程突然终止测试真实崩溃；用可控写入失败测试磁盘/权限错误。恢复后要求：无数据库引用缺失原始文件、无半批业务变更、旧指针保持可读、新指针只指向清单齐全的已发布目录、来源版本不重复、仅导出恢复不再次联网。运行状态、CLI 非零退出码和本地失败事件要一致。CSV 被 Excel 占用造成替换失败也需有可行动错误。

并发检查：两个进程使用同一数据库/输出根目录时，一个按约定等待或明确失败，不能让两次发布竞争覆盖指针；索引忙等待不等于已验证整个流程并发安全。

### T05 · P1 · JD 的“告警 → 定位 → 重跑”及任务从未启动风险缺少验收

位置：`baseline/architecture.md:73–80`、`:222`；`baseline/data_contract.md:195–199`；`baseline/acceptance.md:19`。岗位 JD 第 1、2 项。

逐条质量事件和 HTML 报告可以定位已发生的清洗问题，但缺少告警语义、去重、恢复事件与可复制重跑入口。任务根本没有启动时，该任务自身无法生成失败报告，需有独立的预期执行检查，而非仅在任务内捕获异常。

建议最小闭环采用本地结构化告警文件/数据库与 CLI 状态检查；发布包不必接入真实邮件或 IM。告警至少含运行/批次、阶段、源表、报告期、代码范围、规则、实际值/阈值、影响的因子集合、原始证据位置和明确重跑命令。定时入口使用操作系统调度，提供预期周期检查和最近成功时间；未运行、运行超时、返回非零分开表达。

可执行故障注入矩阵：

| JD 风险 | 注入 | 必须可见的行为 | 修复验收 |
| --- | --- | --- | --- |
| 上游变更/中断 | 必需字段改名、429、临时 5xx、整批空页 | 契约或网络告警，保留请求/响应及重试记录，不伪装成功 | 源夹具恢复后只重跑失败范围，成功指针完整发布 |
| 定时任务失败 | 进程非零退出、超时杀死、错过预期执行且无 `runs` 记录 | 独立检查生成任务失败/超时/未启动事件 | 调度补跑完成，告警有恢复状态与原事件关联 |
| 数据静默错误 | 金额被乘 100、全字段转 null、行数骤降、页重复 | 即使 HTTP 成功也触发单位一致性、空值/覆盖率/行数规则 | 修正后增量与全量相符，异常明确解除 |
| 表/字段口径混乱 | 营业总收入代替营业收入、累计混单季、CNY 混其他币种、合并混母公司 | 字典/契约一致性失败，因子停止错误计算 | 采用正确映射版本重建，源事实未被误记更正 |

相同故障连续两次只产生约定的去重更新；故障修复有一次恢复事件。测试告警接收端使用本地假实现，不真实发送外部通知。验收必须实际复制记录中的重跑命令完成恢复，不能只核对提示文本。

### T06 · P1 · 质量指标已有分母说明，但缺少可手算闭环与新鲜度口径

位置：`baseline/data_contract.md:195–199`；`baseline/architecture.md:50`、`:180–181`。

需要明确质量指标描述的是本次输入、现有数据集、增量变更还是发布输出。否则“本次只有一条更正”会被误判成行数暴跌，或重复页提高覆盖率。不适用排除已说明，但应补充适用分母为 0 的结果；NULL 与 error/历史不足须分开。

反例与验收：4 条适用记录中 1 条为空，另有 1 条不适用记录，则缺失率为 1/4；同一条记录有 3 个异常事件，异常记录率仍为 1/4。预期 4 公司有 3 个唯一业务键且重复页多出 2 行，覆盖率仍为 3/4。分母为 0 时结果为“无适用数据”，不能发布为 0% 正常。增量只有 1 条更正时，当前完整数据集覆盖率不应降为 1/4；来源本次扫描覆盖率可以另外报告。

对“新鲜度”至少区分最近成功扫描时间、最近来源内容变更时间及预期报告披露覆盖。固定历史期间的财务金额长时间不变属于正常情况，不能沿用行情按分钟更新的阈值；连续响应完全相同也不能直接判定为正常。使用固定时钟和预期周期夹具验证过期/未到期边界。

### T07 · P1 · PIT、时区与规则选择需要精确边界测试

位置：`baseline/architecture.md:222`；`baseline/data_contract.md:23`、`:183–191`；`baseline/acceptance.md:45–49`。

时间方向已经正确，但“公告日结束”“as_of 当日结束”、相等是否可见和 naive 时间处理必须固定；默认 operating-system 时区不同不能改变结果。回放清单中没有响应完成时间的早期 `bank_probe.json` 已被源验证文档识别，不应升级为严格 observed 样例。

验收：固定源日期为 2025-04-03、系统首次观察为带 UTC 偏移的精确时间，在可用边界前 1 微秒、恰好边界和后 1 微秒查询；同一瞬间使用 `+08:00` 与 `Z` 参数应完全一致。日期型查询与显式该日结束查询一致。设置主机时区不同或仅对转换入口注入不同默认时区，输出必须不变。未带偏移的精确时间按明确约定解释或拒绝，不能由主机猜测。

另测报表错开披露、参照季度晚更正、旧年度更正不能替代最新报告、源时间在未来、日期缺失、日期精度与时间精度混用、原样重放不改 `first_seen_at`。比较不同 `temporal_mode` 的因子身份，不能相互覆盖。当前快照查询过去应明确无数据。对历史处理规则回放与当前规则重建分别指定版本，以免把可重新计算误说成曾实际发布。

### T08 · P1 · 离线样例与在线门槛需要覆盖全部公式和真实分页

位置：`baseline/acceptance.md:58`、`:62–66`；`baseline/source_validation.md:7–13`。

“在线验证是可选外部集成检查”与后文“在线必需”可解释为日常单元测试可选、最终交付验收必需，应在命令及结果记录中明确这一区别。

目前真实证据只有 3 家公司的同一个年报，不能演示单季度差分、去年同季度和环比的真实计算。离线演示需要补齐足够的连续期间：至少能够真实计算 15 个因子且含跨年 Q1 的同比/环比，不要求每个因子每行都有值。人工边界夹具保持独立；不能将伪造的历史观察时间拼入真实样例。

最终在线验收除 3×8×3 和默认 50 公司外，应显式将 `page_size` 调小触发两页以上，再验证总数、唯一键和漏页。采样名单、报告期和预期覆盖依据保存到清单；不是硬要求上市前/未披露期间必须有记录，但每个缺口须有解释或失败状态。

独立原年报核对保留报告名称、链接或本地文件、页码、单位及对照值。源端多个接口的完美一致只能证明同源一致，不能证明真实公告口径完全正确。若无法核验重述基础，则相关季度结果继续携带限制标记。

### T09 · P1 · Parquet/数据字典缺位，数据库调优缺少可展示证据

位置：`baseline/architecture.md:20–29`、`:142–162`、`:111–125`；岗位 JD 任职要求 5、6、9。

SQLite 与 CSV 足以完成机试基础范围，但用户希望真实工程项目，JD 又直接要求 Parquet 和分区认知，建议加一个简洁的 PyArrow 导出边界，而非另建数据湖系统。需要约定字段、nullable、单位、元数据、处理版本和分区策略，支持与 CSV/数据库一致的读取。50 家×16 期的数据很小，不能按股票×季度制造大量微小文件；可选单文件或按报告年分区，说明尺度阈值和读取过滤方式。

验收：读取导出 Parquet 后与相同运行 CSV/SQL 结果逐项比较，检查代码保留零、日期类型、NULL、有限浮点、单位/版本 metadata。仅一条公司更新后重新发布完整分区，确保删除/失效的旧行没有混回，读者不能看到一半新一半旧的分区。文件清单至少列文件数、行数、字节数、分区键；按公司/报告期过滤应与完整读取再过滤一致。数据字典分别列字段与因子，带来源、含义、单位、空值语义和适用范围。

数据库验收保留公司/期间查询、observed 查询和受影响依赖查询的 `EXPLAIN QUERY PLAN`；用确定性生成的合成规模样例做选择性查询与索引前后对比，记录数据量、文件大小、环境、耗时和查询结果一致性。此性能样例不放进真实财务演示中。不要声称在 2,400 条报表上完成了生产规模性能优化；无需为 JD 增加服务端数据库，但需能够解释迁移边界和真实瓶颈。

### T10 · P1 · EXE 验收应证明隔离环境和运行入口行为

位置：`baseline/architecture.md:130`、`:220–222`；`baseline/acceptance.md:68`、`:104–108`。

在构建机器上清除 PATH 并运行 EXE，只能做冒烟检查，无法证明不依赖 Python/已装 DLL/证书。应在独立 Windows 沙箱、虚拟机或实际干净电脑完成断网演示，记录真实环境和产物摘要；无法做时明确标为未验收。

验收：中文且有空格的解压路径、从任意目录启动、无 Python、断网运行、输出目录不可写后显式 `--output` 恢复、双击零参数、命令行参数模式、线上证书及真实联网小样本。命令行执行必须返回退出码并退出，只有实际双击交互入口可按设计保留窗口；不能让自动化命令无条件 `input()` 卡住。

离线执行不得发出网络请求，静态 HTML 不加载远程资源。比较 EXE 与同版本源码离线结果，规范业务行和输入依赖摘要一致。许可证、真实样例来源、SHA-256 清单和入口说明齐全；清单中的样例或输出若被修改，校验明确失败。

### T11 · P2 · 现有 probe 的容错行为弱于后续采集器约定

位置：`scripts/probe_source.py:58–89`；`baseline/architecture.md:44–48`；`baseline/source_validation.md:81`。

本轮离线 mock 已复现：HTTP 403 作为 `URLError` 被请求 3 次；429 的 `Retry-After: 120` 被忽略，只等待 `[1, 2, 4]` 秒。字段存在但金额为 `"corrupt"`、公告为 null 仍返回 ok；除首行外的异常行和 count 不一致也不检查。probe 是字段可行性工具，这些现象不能推断真实金融值一定错，但不能直接照搬为生产适配器。

建议 probe 成功含义维持“首条返回身份正确且声明字段存在”，完整采集器另实施字段类型/单位/时间、分页一致性和 HTTP 错误分类。或改进 probe 并明确失败状态。HTTP 错误记录应保留状态码、`Retry-After` 及适度错误响应上下文，便于判断权限拒绝、参数错与临时中断。

验收：403/其他非重试 4xx 一次即失败；超时/429/可重试 5xx 按最大次数和退避约定执行；429 在有限且有效的 `Retry-After` 范围内等待。字段改名和金额非法类型产生不同可定位事件；全部结果行与分页元数据校验。测试通过固定时钟、假响应和 sleep spy 验证，不真正等待或访问外网。
