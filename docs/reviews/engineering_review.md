# 工程与运维独立评审

评审日期：2026-10-13。评审对象是现有设计与验证脚本，不是尚未完成的业务流水线。已完整阅读题目、README、架构、数据契约、验收方案、源验证记录、岗位 JD 与 `scripts/probe_source.py`。本文只给出修订建议，没有实现或运行业务验收。

## 1. 结论与边界

目前方案的基础方向合理：财报口径先于计算，真实原始响应可追溯，金融计算与网络/数据库写入分离，SQLite 降低部署成本，离线与在线共用处理链路。题目提出的一周交付、普通 Windows 电脑演示和完整源代码，支持选择单机模块化项目。

但不能据此评价为“已经完善”。现有文档在数据可信度与运维闭环上仍偏重结果说明，缺少执行契约：哪些质量问题阻止发布、失败究竟停在哪一批、如何只恢复未完成工作、规则升级后怎样重现旧结果、双击与调度重叠如何处理。岗位 JD 将这两类能力合计列为 55%，应进入本次交付主线。

项目完整性应体现在可信数据、恢复能力、稳定运行入口与维护说明。应保留单机部署，同时增加必要的内部职责边界；不需要增加服务集群、消息队列、通用 DAG 引擎或大量空接口。

优先级约定：P0 是实现前必须明确的正确性契约；P1 是本次正式交付应完成的工程能力；P2 是有价值但可以在主链路稳定后补充的增强。时间代价是工程工作量估计，部分共享实现，不能直接逐项相加为总工期。

## 2. 分级问题

### ENG-01 · P0：质量报告尚未成为发布门禁

- 现有位置：[架构 §4、§6、§9](../architecture.md)，尤其 `quality_events` 表及退出码；[数据契约 §9](../data_contract.md)；[验收 §1](../acceptance.md) 的“数据质量附加项”。
- 具体反例：源接口仍返回 HTTP 200，某字段全部变成 NULL，所有请求成功、特征全部为 `missing_input`。项目可以生成一份完整 HTML，但缺少规则决定是否允许更新 `latest.json`。另一个反例是公司池意外只剩 10 家，结果内部计算全正确却漏掉 40 家。
- 建议修订：每阶段返回统一 `GateResult`，包含规则编号、严重性、范围、指标分子/分母、阈值、通过情况。明确硬错误与软警告：业务身份/契约错误、计划页未完成、重复页、无法解释的范围丢失、时间证据错误阻止发布；亏损、合理负权益、金融比率极端值按适用规则保留并警告。不能把“所有财务字段必须非空”写成一条通用硬规则。
- 成功契约：`succeeded` 表示计划完成、必需门禁通过、可信结果提交、全部必需产物发布。`succeeded` 可以带软警告；警告汇总必须出现在运行摘要。失败或未完成运行可以留下诊断产物，但不能冒充最近成功的数据集。
- 代价与验收：约 0.5 天形成规则结果模型与门禁汇总。至少验证“全空字段”“计划覆盖下降”“正常亏损警告”三个独立案例；前两个按明确策略阻止成功指针更新，后一个保留结果。

### ENG-02 · P0：失败恢复缺少持久化工作计划与提交语义

- 现有位置：[架构 §8，约第 195 行](../architecture.md) 的“支持恢复重试”；§6 的“一批变更与其派生特征”；[验收 §2](../acceptance.md) 的分页失败、事务中断。
- 具体反例：第 143 页失败后进程退出，只有原始页和错误日志。重启时无法可靠知道总共计划多少页、哪些已验证、哪份配置对应这些页。如果已成功的其他批次进入默认数据库查询，而 `latest.json` 仍指旧输出，查询与导出还可能展示两代结果。
- 建议修订：网络访问前持久化 `run_plan`，冻结实际公司名单、扫描/输出期间、报表类型、源契约版本与请求批次。持久化 `work_units` 和 `work_attempts`：工作单元使用稳定请求身份，尝试另记时间、HTTP/业务状态、页摘要、原始文件、重试次数与错误，不把 attempt 当业务版本。分页必须在同一工作单元内检查页数和键集合，恢复不能把旧页与变化后的新页拼成一份未验证快照。
- 建议提交方式：本项目约 2,400 张报表，优先收齐、归档、验证并在短事务内一次提交本 run 的可信业务版本、清洗结果与特征。控制表、失败尝试与原始证据独立持久化；HTTP 等待与文件导出不占用业务写事务。这样无需为首版建立复杂的分批可见性系统。若实际实现选择逐批提交，则必须追加发布代次/清单约束，使正式查询只读取某个完整发布的数据集合，不能依赖 `latest.json` 一项掩盖数据库中的半代数据。
- 恢复接口：`resume --run-id <id>` 读取原计划和已完成工作，不重新抽取公司池；重试失败或未完成单元。源契约/输入范围变化应新开 run 并关联 `parent_run_id`。已提交但导出失败走 `export --run-id <id>`，不重新抓取源数据。恢复后的发布拥有新尝试信息，保留失败历史。
- 代价与验收：约 0.5—1 天；新增少量控制表与两个恢复入口。强制结束进程、失败页恢复、提交后导出失败都应能重现；恢复后结果与一次成功运行一致，业务版本不重复。

### ENG-03 · P0：规则或映射升级可能覆盖历史清洗结果

- 现有位置：[架构 §6](../architecture.md) `clean_income/clean_balance/clean_indicator` 以 `version_id` 为主键；§8 要求映射、清洗阈值或公式变化触发重建；`feature_inputs` 只指向 `version_id`。
- 具体反例：同一原始资产负债表在规则 v1 下接受，在规则 v2 下隔离。如果覆盖该 `version_id` 的清洗状态，旧特征仍有输入关系，却无法查到当时使用的清洗结果。若单位映射修复被计为源版本更正，则“上游修订数量”也会失真。
- 建议修订：区分原始来源记录版本、规范化版本、清洗规则版本与公式版本。清洗结果采用不可变 `clean_revision_id`，其身份至少包含来源记录版本、规范化版本和清洗规则版本；`feature_inputs` 指向实际使用的清洗修订与字段，必要时同时保留原始记录引用。映射升级是派生解释的变化，不能伪装成真实抓取时发现了新的源修订。可以将来源内容摘要和规范业务摘要分开保存。
- 幂等契约：相同输入版本、规范化/规则/公式版本、时间模式产生相同特征身份。重跑只新增运行观察与尝试记录，不新增业务/特征版本；格式、输出路径或 HTML 展示改变不触发金融计算重建。重建时保留原首次观察证据，不用重建时间替代源观察时间。
- 代价与验收：约 0.5 天调整主键、输入关系与指纹范围。验证两套规则结果同时可查询；旧特征能还原对应清洗修订；规则升级的源新增/修订计数均为 0。

### ENG-04 · P1：单写者声明不能防止两个完整任务重叠

- 现有位置：[架构 §6，约第 162 行](../architecture.md) 的“默认单写入进程”和忙等待超时；§9 的双击 EXE 与运行入口。
- 具体反例：定时任务未结束，维护者双击执行重建。SQLite 可以依次接受两个事务，但两个任务仍会重复采集、读到不同输入、竞争运行目录或更新成功指针。`busy_timeout` 处理锁等待，不能为完整生产流程提供互斥。
- 建议修订：对相同解析后绝对数据目录建立进程级互斥，所有 `run/resume/rebuild/export/数据库迁移` 入口统一进入。优先使用成熟的操作系统文件锁实现，锁定范围和等待时间明确；锁文件即使残留也不以“文件存在”永久判定占用。只读查询不抢生产锁。进程结束后锁自动释放，下一次拿锁后再把未完成 run 标为 interrupted，并给出恢复入口。不要根据 PID 数字或超时直接删除仍被其他进程持有的锁。
- SQLite 设置：首版维持本地磁盘、单写者与默认回滚日志，显式开启外键、忙等待与确定的事务策略。长网络采集放在事务外。WAL 不自动成为性能开关；它仍只有一个写者，并增加检查点与文件生命周期要求。[SQLite 官方锁说明](https://www.sqlite.org/lockingv3.html)、[WAL 说明](https://www.sqlite.org/wal.html)支持这些限制。
- 代价与验收：约 0.25—0.5 天；模拟两个命令争用同一目录及运行进程被终止。第二个命令应得到可行动的占用信息或有限等待，不能悄悄再跑一份。

### ENG-05 · P1：Parquet 需要加入交付，但不能形成第二份权威数据库

- 现有位置：[架构 §2、§5](../architecture.md) 当前仅 SQLite 与 CSV；[JD 任职要求 5](../job_description.md) 明确列式存储、分区和小文件认知。
- 具体反例：实现时直接对 SQLite 和 Parquet 同时增量 upsert，进程在第二次写入前退出，数据库有新值、文件仍是旧值。按“公司×季度×特征”拆文件又会把约 9,000 个特征值拆成大量小文件，目录管理成本大于读取收益。
- 建议修订：SQLite 是控制状态、来源/清洗版本、特征版本与血缘的权威存储；Parquet 是从已提交版本集合生成的不可变分析快照，可由数据库重建。CSV 服务人工查看，Parquet 服务 pandas/Arrow 列选择与后续研究，不对 Parquet 维护另一套独立版本排序逻辑。[Arrow 官方文档](https://arrow.apache.org/docs/python/parquet.html)说明了列选择与分区读取能力。
- 首版布局：每个发布 run 按数据集写少量文件，例如 `financial_income.parquet`、`financial_balance.parquet`、`financial_indicator.parquet`、`features.parquet`。本样本不按公司分区，也不为每个增量 append 一个小文件。数据量实际扩大后再比较 `report_year` 等低基数分区；分区键与业务查询应匹配。
- 一致性：manifest 记录精确输入/特征版本集合或可复现的冻结发布代次、schema/公式/规则版本、行数、文件字节数和校验值。临时文件写入与成功指针位于同一文件系统；全部写完、回读核对 schema/行数/摘要后发布，再更新 `latest.json`。发布中断可从提交版本重导出；失败不得使已完成快照失效。
- 代价与验收：约 0.5 天；新增 PyArrow 运行依赖与发布校验，包体会增长。验证 SQLite 选定集合、CSV 与 Parquet 数值及 NULL 状态等价；修改或丢失一个 Parquet 文件时能定位并重建。

### ENG-06 · P1：“约 8 个核心文件”限制会把不同变更原因塞在一起

- 现有位置：[架构 §4，约第 73—85 行](../architecture.md) 及目标目录；`storage.py` 同时包含迁移、来源版本、时点 SQL、增量依赖；`features.py` 同时包含公式、季度关联、注册与依赖传播；`eastmoney.py` 同时包含网络、分页、映射与契约。
- 具体反例：增加一个财务指标只需改公式，却必须接触包括 SQL 血缘重算的巨大文件；源字段改名与 HTTP 429 重试策略落在同一模块，使单元测试必须了解网络与财务口径。质量聚合、输出文件与发布状态都进入 `reporting.py` 时，其职责也会膨胀。
- 建议修订：按维护时会一起变化的责任形成包。模块划分、具体接口及依赖方向见下文。公式、SQL、网络策略、门禁和发布协议各有明确归属；不以文件数量少证明精简。反过来也不为每条规则、每个因子或每张表建立一个类，避免空接口、通用仓储基类、只转发一行的服务层。
- 代价与验收：在实现前调整约 0.25 天；晚于业务实现再拆成本明显更高。维护说明应演示“新增一个因子”和“修复一个源映射”，指出唯一业务改动位置及需补的测试。

### ENG-07 · P1：告警、定位、重跑缺少明确产物与恢复关系

- 现有位置：[架构 §6](../architecture.md) 的 `quality_events`；[数据契约 §9](../data_contract.md) 的 HTML；[JD 职责 1](../job_description.md) 的告警闭环。
- 具体反例：维护者收到“本次缺失率为 20%”，仍不知道出错表、失败批次、哪几家企业、哪张原始页、哪些下游因子受影响，也不知道应该 resume 还是 rebuild。重跑成功后，原告警仍只能靠人工猜测是否解除。
- 建议修订：`quality_events` 保留逐条规则证据；另生成聚合 `alerts.json` 和结构化告警状态。每条告警至少含 `alert_id/rule_id/severity/run_id/work_unit_id/table/field/scope/expected/actual/threshold/raw_reference/affected_downstream/recommended_action/recovery_run_id/status`。大影响面使用摘要、计数及详情引用，避免将所有依赖塞成一段日志。未识别业务键时按页与行号定位。
- 本地闭环：终端明确非零状态，HTML 展示告警及可复制的恢复命令；恢复运行引用原 run/告警，相关工作重新通过后将告警记为 recovered，保留首次发现与最后检查记录。清除“请求失败”不等于清除“源字段缺失”，不能执行一次命令就统一关闭全部告警。邮件、Slack 或 webhook 不是当前必要条件，不在本轮自动发送外部通知。
- 代价与验收：约 0.5 天，与 ENG-01/02 共享数据模型。演示一条失败页告警，从告警定位到 raw 引用，再执行恢复，最后显示哪条告警经哪个 run 恢复。

### ENG-08 · P1：定时任务从未启动时，普通流水线日志发现不了

- 现有位置：[架构 §9](../architecture.md) 只有手工入口，末尾只提定期执行说明；[JD 职责 1、2](../job_description.md) 明确任务失败和调度维护。
- 具体反例：Windows 任务计划因路径或账户问题连续两天未启动 Python，项目没有新日志，也没有异常 run。仅检查最近一次运行的 HTML 会看到一份过去的“成功”报告。反例二是合法财报连续几个月数值不变，却被“字段更新频率”误报为失效。
- 建议修订：交付可审查的 Windows Task Scheduler 示例与安装/撤销脚本，安装由用户显式执行，脚本不自动改变机器任务。任务引用发布 EXE 的绝对路径与确定配置，非交互运行；项目级锁防重叠。另提供 `health` 检查：最后尝试、最后成功扫描、预期调度时间、容许延迟、未完成 run、当前数据发布年龄。可由独立的检查任务调用，不能让监测只依赖被监测任务自身成功执行。
- 时间口径：计划采用用户的 Asia/Shanghai 时区并在记录中写明，状态时间内部统一 UTC。区分“最近成功抓取时间”和“内容实际改变频率”：稳定历史财报长期不变是正常，接口长期没有成功访问则是采集新鲜度异常。新报告覆盖不足依计划/披露证据检查，不用旧报告金额是否变化推断源健康。
- 代价与验收：约 0.25—0.5 天。对健康检查注入固定当前时间并模拟任务从未执行、执行失败、历史财报不变三种情况。

### ENG-09 · P1：指标与数据字典尚不足以支持可量化运维

- 现有位置：[数据契约 §1、§2、§9](../data_contract.md)；[架构 §6](../architecture.md) 的数据库对象列表；[JD 任职要求 7、9](../job_description.md)。
- 具体反例：两次都配置 `company_limit=50`，但重新生成的公司名单不同。只比较 50 家与 50 家的行数不会发现换样本，也不能将两次空值率下降理解为修复成功。采集 16 期但仅刷新 8 期时，扫描数与最终导出数不是同一分母。
- 建议修订：记录解析后的 universe 摘要、实际扫描范围、输出范围、来源契约、字段适用性、规则/公式版本。比较基线以实际范围指纹匹配；规则或适用性版本改变时标注比较限制。覆盖率按已冻结的预期业务键集合计算，把未上市、未披露、采集失败、解析失败、隔离、成功缺失分别解释；不直接把 50×16×3 全部当已证明应披露的数量。
- 指标至少包含请求/页成功率、重复页、原始记录数与唯一键数、覆盖率、字段空值率、隔离率、变更数、特征有效率、新鲜度与各阶段耗时。分母为 0 返回“无适用记录”，不能显示 0% 作为合格。计数应满足可核对的守恒关系，例如源行 = 接受 + 重复 + 隔离，特征目标键 = 有效 + 各原因无效。
- 字典：维护字段来源、语义、类型、单位、主键、累计/存量属性、时间精度、适用范围、缺失处理、质量规则、下游因子及版本。尽量由代码使用的映射/规则/特征注册元数据生成表格，文档是可读输出；不用人工分别维护三套字段定义。
- 代价与验收：约 0.5 天，与报告实现共享。核验可比/不可比基线、零分母、扫描范围小于输出范围、公司池变化和字典与 schema 一致性。

### ENG-10 · P1：数据库完整性、迁移与备份缺少操作约定

- 现有位置：[架构 §6](../architecture.md) 只有对象/索引方向和编号迁移；[验收 §3](../acceptance.md) 尚无迁移、外键与备份恢复场景。
- 具体反例：`feature_inputs` 插入不存在的 `version_id`，如果连接未开启外键，数据血缘会悄悄断裂。新版本程序对旧数据库写了一半 schema 后失败，也可能使旧程序无法再读。复制正在使用的 SQLite 主文件不等于得到一致备份，尤其不能遗漏 WAL 的持久状态。
- 建议修订：数据库连接集中配置外键、超时与事务；为业务版本、清洗修订、特征身份设置明确 UNIQUE，为血缘与页引用建立 FOREIGN KEY；控制状态/报表类型设可验证约束。迁移放在编号 SQL/小迁移函数中，登记 schema 版本，旧版本与新版本兼容范围明确。不可恢复的迁移前用 SQLite backup API 生成备份；不要只在文档中告诉人复制主文件。[SQLite 外键文档](https://www.sqlite.org/foreignkeys.html)、[备份文档](https://www.sqlite.org/backup.html)、[WAL 文件说明](https://www.sqlite.org/wal.html)说明相关行为。
- 查询与性能：提供一个按公司/期间/时点选择最新可见版本的 SQL 示例，附实际数据集的 `EXPLAIN QUERY PLAN` 与查询时延。索引应围绕该查询验证，不能“每列各建一个索引”后声称调优完成。[SQLite 官方查询计划说明](https://www.sqlite.org/eqp.html)可用于检查，但测试不应硬编码整段 plan 文本，因为显示格式不是稳定接口。
- 代价与验收：约 0.25—0.5 天。测外键拒绝孤儿、旧 schema 升级失败回滚、备份恢复后特征与血缘可查询。

### ENG-11 · P1：发布环境验证应提前，运行模式应隔离

- 现有位置：[架构 §2、§9](../architecture.md)，[验收 §5、§6](../acceptance.md) 将打包主要放在第 6 天。
- 具体反例：开发机 Conda 环境能够找到证书、Arrow 动态库和模板，发布 EXE 在干净 Windows 上缺资源。在线与 demo 共用默认数据库时，示例重放也可能混入日常数据。所有 EXE 结束都等待按键，则定时任务会永不退出。
- 建议修订：第 1 天完成一个含配置和样例资源的最小 EXE 冒烟检查，后续扩展依赖时继续检查资源收集；正式版本记录实际 Python/SQLite/依赖/架构，而不是只锁 pip 包。源码安装、开发检查与发布构建的依赖分别锁定，但不要求使用者学习额外包管理器。新加入 PyArrow 必须同时验证冻结产物。
- 发布方式：建议先交付 PyInstaller `onedir` 目录压缩包，含一个可执行入口；若再提供 `onefile`，单独验收解包资源、启动耗时和写入路径，不能把“只有一个 EXE 文件”当作完整交付前提。PyInstaller 官方说明区分了两种运行/资源路径，输出不应写入冻结资源目录。[打包模式](https://pyinstaller.org/en/stable/operating-mode.html)、[运行路径](https://pyinstaller.org/en/stable/runtime-information.html)。
- 运行体验：demo 默认写独立演示输出目录，online 使用显式配置数据目录；两者共用算法与 schema，不混入同一生产库。命令行默认不等待按键，双击体验可由 `demo.cmd` 或显式 `--interactive` 提供；保留退出码并在中文说明中展示一次完整操作。配置路径、模板资源路径与用户输出路径分别处理，任何工作目录启动都可运行。
- 本机实测：Python 3.12.7，Anaconda 构建，`sqlite3.sqlite_version=3.45.3`。这是当前开发环境事实，不是最终发布包版本，也不是 WAL 并发或 EXE 已验收的证明。本机 sqlite3 标准库版本不能仅靠 `requirements.lock` 锁定。
- 代价与验收：早期冒烟约 0.25 天，最终干净机器验证约 0.5 天。离线、无 Python、中文/空格路径、不同工作目录、不可写输出目录、非交互退出与 HTTPS 证书均应检查。

### ENG-12 · P2：规模与性能认识需要实测，验证脚本能力不能外推

- 现有位置：[架构 §1](../architecture.md) 的理论 2,400 张报表与§6 的百万级扩展判断；[源验证 §1](../source_validation.md)；`scripts/probe_source.py:46—47` 固定第一页/一条记录。
- 具体反例：业务采集如果按每公司每报告每期单独请求，2,400 次请求仅 1 秒间隔就至少约 40 分钟；如果真实接口支持 20 公司批次并每批只需一页，则 50×16×3 对应约 144 批，最低间隔约 2.4 分钟。二者实际耗时都还取决于请求响应和重试。12 项单行成功不能证明批量过滤、全页完整性或大范围耗时。
- 建议修订：保留 probe 为诊断工具，明确它不是生产 adapter。生产采集另测候选池分页、代码批次过滤、稳定排序、重复页与完整性。验证脚本覆盖保存和粗粒度错误处理是其当前边界，不把这些行为复制成正式归档/重试策略。
- 性能证据：默认数据集记录真实公司数、报表/版本/特征数、请求数、页数、各阶段耗时、重试耗时、内存峰值、SQLite/Parquet 字节数与文件数，区分初次建立、无变更增量与历史更正重算。较大人工数据集只能验证计算/查询性能，醒目标注，不能充当真实采集量。
- 代价与验收：约 0.25 天。用实际瓶颈决定是否需要年度 Parquet 分区、更大事务批次或其他数据库；不要用一个未经实测的“百万级”阈值决定迁移存储，也不要为小样本提前引入 Dask。

## 3. 建议职责结构

这是一份边界建议，不要求一开始创建所有空文件，也不要求每个文件固定行数。公式与输入关系、来源协议与字段含义、数据版本与发布文件有不同维护原因，应该能独立修改和验证。

```text
src/finpipe/
├── cli.py                         # 命令解析、结果展示、退出码
├── config.py                      # 配置、路径、版本范围校验
├── domain.py                      # 少量共用身份/枚举/结果数据类
├── providers/eastmoney/
│   ├── client.py                  # 限速、超时、HTTP重试
│   ├── adapter.py                 # 请求批次、分页、业务响应
│   └── mapping.py                 # 报表字段契约与单位元数据
├── storage/
│   ├── database.py                # 连接、事务、迁移、备份
│   ├── runs.py                    # 工作计划、尝试、告警恢复关系
│   ├── reports.py                 # 来源/清洗版本写入、PIT SQL
│   ├── features.py                # 特征身份、输入血缘、影响查询
│   └── migrations/               # 编号迁移
├── processing/
│   ├── normalize.py               # 类型、单位、身份规范化
│   └── cleaning.py                # 缺失解释与行/字段清洗状态
├── features/
│   ├── registry.py                # FeatureSpec及明确注册项
│   ├── financial.py               # 15个纯计算函数与安全数学
│   ├── temporal.py                # 精确期间关联、累计转单季度
│   └── dependencies.py            # 受影响集合与未生成节点推导
├── quality/
│   ├── rules.py                   # 规则结果、严重性、阶段门禁
│   ├── metrics.py                 # 分母、覆盖、基线、新鲜度
│   └── alerts.py                  # 聚合告警与恢复状态判断
├── pipeline/
│   ├── plan.py                    # 冻结名单、请求/输出工作计划
│   ├── service.py                 # 执行顺序、错误边界、恢复
│   └── lock.py                    # 同目录生产任务互斥
└── reporting/
    ├── export.py                  # CSV/Parquet、manifest、发布
    ├── html.py                    # 展示质量事件与可行动告警
    └── templates/                # 静态离线HTML资源
```

`__init__.py`、`__main__.py`、随包真实样例及可选回测包按现有方案补齐。正常组织约二十余个有明确职责的代码模块，比八个巨型文件更适合多人或后续人工维护；不是把模块数当成评估指标。

依赖方向建议为：CLI → 编排 → 适配器/存储/规范化/计算/质量/输出。计算与质量规则接收规范输入并返回数据，不自行访问网络、打开数据库或发布文件。存储不 import 编排或 CLI。报告只展示既有指标和告警，不偷偷重新执行一套质量判定。`service.py` 允许协调多层，但不包含长 SQL、15 个公式或 HTTP 重试细节。

不需要所有组件都定义 ABC。来源适配器与特征注册保留现有两个主要扩展点；新增来源后再判断共享网络策略是否值得抽取。存储通过少量明确操作表达用途，例如 `select_visible_reports`、`persist_run_results`、`find_affected_features`，不用万能 `Repository[T]` 掩盖金融身份和事务边界。

## 4. 运行状态与闭环最小契约

建议把状态和阶段分开记录，而不是增加大量组合状态：

| 对象 | 状态/阶段 | 约束 |
| --- | --- | --- |
| run | `planned/running/succeeded/partial/failed/interrupted` | `succeeded`必须满足ENG-01的完整成功条件 |
| run阶段 | `acquire/normalize/clean/features/commit/publish` | 记录最近完成阶段；提交后发布失败可重导出 |
| work_unit | `pending/acquired/validated/failed` | 每次HTTP/业务尝试另存；验证包含分页完整性 |
| alert | `open/recovered`，外加恢复run引用 | 相关条件经恢复重新检查通过才解除 |
| publication | 不可变manifest + 最近成功指针 | 精确选定版本集合，失败不能指向半成品 |

本次项目不需要自动重试无限循环、自动跳过失败历史、复杂告警确认工作流。可维护者的一次操作应是“看告警上下文 → 执行给出的恢复命令 → 检查恢复 run 与告警状态”，不用翻数据库手工改状态。

## 5. 保留、补强与延后

| 决策 | 内容 | 理由 |
| --- | --- | --- |
| 保留 | Python、pandas/NumPy、requests、SQLite、TOML、单机CLI | 符合题目规模与普通Windows演示要求 |
| 保留 | 真实原始样例、离线在线共用主链路、PIT限制明确、版本追溯 | 是金融正确性与答辩可信度的基础 |
| 保留 | 纯计算函数、15个口径、长表、直接注册特征 | 可解释且已有明确扩展点 |
| 补强 | 质量门禁、批次计划、状态、resume/export、告警恢复关系 | 将监控与生产闭环落到可运行行为 |
| 补强 | 版本化清洗修订、精确输入血缘、分层指纹 | 保证规则升级后历史可重现 |
| 补强 | 实际范围基线、字典元数据、调度示例、独立health检查 | 对应JD的口径管理、运行维护与量化监控 |
| 补强 | PyArrow、Parquet快照、manifest、列选择示例 | 有直接JD价值，又不增加第二权威存储 |
| 补强 | 目录锁、迁移/备份、发布早验收、规模实测 | 使维护者能稳定运行与排障 |
| 延后 | 回测的复杂交易限制和行情自动采集 | 独立附加模块，历史财报快照不足时不能声称真实回测 |
| 延后 | Dask、分布式调度、多写入数据库、消息队列 | 当前量级没有验证出的需求 |
| 延后 | 股票分钟线、期货主力、期权、指数全套管理 | JD给出岗位范围，机试仍是财报工程，不能全塞进本项目 |
| 延后 | 外部通知渠道、GUI、动态插件、通用数据治理平台 | 本地闭环先完成；接口需求发生后再扩展 |

## 6. 一天级工程顺序

此安排含题目主线，不是给现有设计继续追加一周文档工作。不同agent可以承担实现与验证，但共享数据契约、状态/提交协议必须先冻结。

| 日序 | 主要结果 | 完成判断 |
| --- | --- | --- |
| 第1天 | 冻结P0契约；职责包、CLI/配置/锁、数据库迁移；最小EXE资源冒烟 | 能安装/运行，计划可查看；干净目录与中文路径能加载随包样例 |
| 第2天 | 工作计划/尝试表、实际样本冻结、正式分页与原始归档、失败恢复 | 离线/在线接入同一链路；失败页可定位并按原计划恢复 |
| 第3天 | 版本化规范/清洗、质量规则、门禁与逐条证据 | 单位/缺失/冲突/时间证据手算与硬软规则验证通过 |
| 第4天 | PIT查询、15个特征、精确输入关系、CSV/Parquet/manifest/HTML | 一次完整结果发布；历史查询与输入来源可解释 |
| 第5天 | 增量依赖传播、规则升级、告警恢复、health与调度示例 | 重复运行零业务新增；人工更正与三类恢复均符合契约 |
| 第6天 | 默认真实范围采集、独立年报核对、规模证据、迁移/备份与EXE隔离验收 | 发布包断网/无Python可运行，源码/EXE结果一致 |
| 第7天 | 修复验收发现、维护手册、交付清单/摘要、演示答辩；有余力做独立附加回测 | 记录真实通过/未通过情况，完整产物可复现 |

优先不应把状态、恢复和打包推到最后一天。它们决定任务能否稳定交付，也会反过来约束存储表与入口设计。可选回测仍保留规划；其工作量不能挤占正确性、真实采集、运维闭环和可执行文件。

## 7. 尚未验证的事项

本评审验证了本机 Python/SQLite 版本，并查阅了 SQLite、Arrow、PyInstaller 官方行为文档；没有运行正式分页、大样本流水线、性能基准、调度或 EXE。以上成本和布局是设计建议，不是测得结果。现有12项接口验证仅证明对应请求的身份与字段存在，后续仍需真正的完整页、源报告和交付环境证据。
