# 实现阶段金融与恢复独立复审

日期：2026-10-13。评审者：`implement_finance`。本轮只读检查主 agent 的 `source_records.py`、`pipeline.py`、`publication.py`、`monitoring.py`、`reconciliation.py` 及其调用边界；没有修改上述源码。

本轮重点是来源事实如何进入正式因子、怎样失效、哪些核对可以叫一致，以及失败后怎样恢复当前健康。先检查业务反例，再检查实现。本文记录代码审查及小型人工模型结果，不能替代验证 agent 的实际端到端、原报告、断网 EXE 和故障恢复验收。

## 1. 已成立的实现边界

- 财务计算按准确报告末日关联，Q1 使用累计值，其他季度只减同年紧邻累计期。加权 ROE 与存量不差分；负利润保留，成长基期非正不硬算百分比。
- `compute_features` 保留十五格，包括有明确状态、真实边界和输入关系的 NULL。正常重复观察不制造新输入身份；处理版本变化与实际来源变化分开。
- 有已知未解决重述或不可比证据时，相关单季差分输出 NULL；普通缺独立核验保留源假设估计及 warning，不冒充原版历史 PIT。
- 增量实现已按改变公司及冻结有限输出范围求值；其他公司的结果保留原版本。未观察到跨公司漏传播路径，仍需由事件验收验证增量与同事实全量等价。
- 发布核验已检查因子目标全集、范围/profile、选中 clean 对应来源、准确输入成员与冻结时间；实际发布时间由 SQL 激活记录，旧候选用预期父 head 限制激活。
- 同源核对明确标 `same_origin_check`。净利率营业收入与营业总收入不同时不强求同源指标吻合，NULL 不算数值匹配。

第一批自有纯计算验证为 44 项测试和 19 项子测试通过，Ruff 通过；本轮没有把这些测试重新计作新的集成验收。

## 2. 本轮发现后已在主代码出现的修订

下列项已将具体反例交给主 agent，并在随后代码读取中看到了对应修订。这里的“已修订”指代码已经出现；完整运行与恢复场景由独立验证记录确认。

| 业务反例 | 已出现的保护 |
| --- | --- |
| R1 在准备快照前失败，R2 补齐并发布，恢复旧 R1 又写缺失状态、污染健康 | `_process` 写状态前及 `resume` 重试采集前比较原计划父 head；不匹配返回 SUPERSEDED |
| 采集失败后，质量阻断覆盖最后健康原因；旧好归档被误当成新扫描 | 按每个来源告警自己的失败时间和失败扫描范围判断恢复；未恢复来源告警保持 scope blocked |
| 后续处理失败覆盖采集失败的恢复义务 | 采集失败使用 `upstream_capture_failed`，与普通处理失败区分 |
| 同页同业务键、金额相同，但币种/时间/范围不同，按行顺序选择 | 最高实际观察时刻的候选增加关键语义比较；不同语义进入 conflict |
| 坏公告/隔离记录仍有有限字段，独立核对只看数值就报 matched | CLI 传真实 clean 质量与时间有效性；核对先判 not_comparable |
| 季度数与累计数仅因金额相等而匹配 | 核对增加期间基础检查；参考元数据保留原文件身份另行准备 |
| 同范围成功快照已经存在，但运行从不传 previous，动态基线永远不足 | 接通 `previous_quality`；仅取同 scope/profile 成功、独立捕获样本，重复重放不扩充样本 |
| NO_CHANGE 跳过质量复核并直接清健康 | 复用原因子，但对当前冻结事实重新执行质量检查，再判断恢复义务 |
| NO_CHANGE 运行关联旧已发布快照，自身没有候选报告，resume 报缺核验 | 已发布快照优先执行验证与回执修复，不伪造候选质量报告 |
| after_prepare 中断后恢复只保留指标、丢掉事件和核对明细 | 原完整 `_report` 持久化；缺原报告明确拒绝恢复 |

独立人工模型曾复现：相同观察时间的 CNY/USD 候选交换行序会交换选中版本；隔离且期间不一致的输入会被判 matched；旧归档在健康原因被覆盖后会解除新来源故障。相关修订不能仅靠代码存在来宣称已经通过真实故障验收。

## 3. 最后读取时仍需收口的项

### F01：明确币种证据被默认来源假设覆盖（P1）

位置：`source_records._source_record` 的 CURRENCY 缺失分支。范围证据已经使用 `setdefault`，币种仍使用 `evidence.update(currency_assumed='CNY', ...)`。

人工纯函数反例：原 `_evidence.currency_assumed='USD'`，并有明确证据定位，CURRENCY 为 NULL。转换后证据变为 CNY，`normalize` 返回 `accepted_with_issues`，没有隔离。原始 HTTP 证据可以仍在归档中，但进入清洗的来源事实已经被改写。

建议：仅在缺币种证据且来源规格明确时补 CNY 假设；保留已有未知或不同币种证据，由清洗规则隔离。验收应核验 CNY 规格补位仍可用，同时已有 USD/unknown 依据不能被覆盖。

### F02：双方缺期间基础时仍可匹配（P2）

位置：`reconciliation.compare_reference`。当前检查左右 `period_basis` 是否相等，双方都缺失时 `None == None`。

人工纯函数反例：合法字段名 `operating_revenue_ytd`，两边都省略期间基础，其余证据及有限数值齐备，结果仍为 matched。正常 CLI 已补规格，因此这是公共函数的边界缺口，不能说所有 CLI 核对都会触发。

建议：双方期间基础须明确且等于当前字段规格的 ytd / point_in_time；缺失或冲突返回 not_comparable，不以未知相等证明口径一致。

### F03：记录成员完整性目前主要依赖数量（P2）

位置：`publication.validate_snapshot`。因子已经比较准确目标全集；记录目前检查数量和所引用因子的输入关系。

静态反例：用同数量的其他公司/期间余额记录替换一个没有被现有十五因子使用的早期余额记录，数量不变，实际因子输入也不变，可能通过验证。正常构建器按 scope 循环创建，因此这里是发布防线完整性问题，尚未执行该故障注入，不能记录为已复现。

建议：像因子一样比较准确源业务键全集，不新增表或抽象。

## 4. 核对与证据的解释边界

- `comparison_coverage` 当前按参考文件记录集合计算，`reference_coverage` 按完整左侧字段集合计算。这两个分母不同，使用者必须知道前者表示本次参考计划的到齐比较，后者表示完整数据被独立参考覆盖的程度。参考样本吻合不能宣传为全部数据已独立核验。
- 新参考元数据明确字段期间并不自动验证重述历史。独立原报告核对仍应保留报告版本、期间、合并范围、币种/单位、页码、文件摘要和差异；一次金额吻合不能推广成所有季度已经可比。
- source_assumed 的季度估计可以支持当前财务分析；真实历史观察之前的正式可交易数据及回测能力仍不能由当前快照推造。
- WAITING_DATA、PUBLISHED、NO_CHANGE 是执行结果；来源告警未恢复时 scope 可以仍 blocked。消费当前结果须继续经过当前健康检查，而不能仅看一次离线处理命令的成功状态。

## 5. 后续验证重点

不新增测试数量目标。优先验证同事实全量/增量一致、最新坏状态立即生效、缺期补齐、冲突解除、旧候选恢复、健康原因连续变化、真实新扫描恢复范围，以及核对的缺证据/不可比/缺键边界。

本轮人工模型只使用 Python 纯函数及内存 SQLite，没有修改业务库、原来源证据或生产包。来源修订含义、独立原报告、实际财报多期覆盖、打包与无 Python Windows 环境均须以各自实际验收记录为准。
